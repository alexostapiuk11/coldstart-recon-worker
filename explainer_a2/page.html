Artifact 2, modules 1–6

An autoscaler is {{def:autoscaler}}. It decides from a signal, a number it can read, such as how many requests are waiting. Artifact 2 asked which signal gives the best trade between cost and p99 latency in a traffic spike. Here p99 is {{def:p99}}, and latency is {{def:latency}}.

The comparison was to be made in a simulator, which is {{def:simulator}}. The simulator was to be trusted only if it passed a test that was pre-registered, meaning {{def:pre-registered}}. It failed that test twice. So the post reports the failure and no ranking of signals, and this page follows the post.

Module 1

Continuous batching and the service curve

The server is vLLM, {{def:vLLM}}. An engine is {{def:engine}}. Here it ran Qwen3-8B on one RTX 4090.

A model writes text one token at a time, and a token is {{def:token}}. An LLM server uses continuous batching, which is {{def:continuous batching}}. Requests join the running batch as they arrive and leave when they finish, and every step produces one token for every request in the batch.

The batch has limits. The setting max-num-seqs is {{def:max-num-seqs}}. The batch also needs room for each conversation’s state, which lives in the KV cache. A KV cache is {{def:KV cache}}. When the cache is full, new arrivals wait.

To see what batching does, the sweep held a fixed number of requests outstanding and measured the server. That is a closed loop, meaning {{def:closed loop}}. The number of requests being served at one moment is the concurrency, which is {{def:concurrency}}. A request is in flight while it is {{def:in flight}}. The sweep used {{c_levels_list}} in flight, with {{runs_level}} runs at each level. The result is the service curve, which is {{def:service curve}}.

Two numbers describe a level. Latency is {{def:latency}}. It is taken here as the median over a run’s requests and then the median of the runs. A median is {{def:median}}. Throughput is {{def:throughput}}, counted in tokens per second. Throughput divided by the requests in flight is the speed each request sees. The bars on the chart span the lowest and highest of the runs.

Module 2

Little’s Law, checked on real data

Little’s Law is {{def:Little's Law}}. In symbols, L = λ × W. L is the average number of requests in the system, λ is the rate at which they arrive and leave, and W is the average time each one spends there. Requests arriving ten per second and staying two seconds each put about twenty in the system.

It holds over any stretch where the system neither fills up nor drains, whatever happens inside. So it can be checked against data: measure two of the three and compute the third.

The load-balancing probes

Before the validation runs, known traffic was sent through RunPod’s load-balancing endpoint to see whether it could carry the test. RunPod is {{def:RunPod}}, a worker is {{def:worker}}, and a load balancer is {{def:load balancer}}. The five probes were run to find out, were not pre-registered, and changed the endpoint’s settings between them on purpose.

Each request records which worker served it and the engine’s own latency for it. From those, the page counts how many requests each worker held at once. A request is placed on its worker from (the time the client saw the answer, minus a return leg of {{return_leg}} s, minus the engine’s latency) to (that time minus the return leg). The return leg is an assumption, about half the load balancer’s overhead when idle.

MEASURED · in-flight counts reconstructed with a {{return_leg}} s return leg · probe 1: {{p1_workers}} workers at the scaler value’s default

The scaler value is {{def:scaler value}}. W is L ÷ λ, the time each request spends in the engine.

On every step W comes out near {{p1_server50}} s, the engine’s own p50 (p50 is {{def:p50}}). Read this check for what it is. Each worker’s intervals are built from the engine’s stamped latencies, so L ÷ λ lands close to their average almost by construction. It shows that the counts and the delivered rate agree. It does not test the law against something independent.

The independent test is the service curve, which was measured separately with a fixed number of requests in flight. Probes 2 and 3 used the same endpoint type with the cap raised, and at low rates one worker carried every request. Each row below takes that worker’s mean in flight, computes W, and compares it with the curve’s latency at that many in flight.

MEASURED · one worker per step · curve interpolated at the mean in flight

W sits below the curve’s latency in every row, by {{ow_below_min}}% to {{ow_below_max}}%. The curve was measured on one host, closed loop. These probes ran on other workers, open loop. The post re-measured another host, {{def:host}}, of the same GPU model and found its latency {{hs_lo_pct}}% to {{hs_hi_pct}}% lower than the curve’s host at {{hs_lvl_lo}} to {{hs_lvl_hi}} in flight. A gap of this size and sign is what a faster host would give. This repository did not test whether that is the cause, and probe 5 is not in the table because the analysis file holds no in-flight counts for probes 4 and 5.

The cap of {{p1_cap}} per worker

In probe 1 the scaler value was at its default. The reconstruction puts each worker’s peak in flight at {{p1_cap}}, except one reading of {{p1_peak_over}}, which the reconstruction can produce by overlapping two neighbouring requests. So the setting acts as a limit of {{p1_cap}} in flight per worker.

Two workers at {{p1_cap}} each is {{p1_ceiling_in_flight}} in flight. At {{p1_w_round}} s per request, Little’s Law turns that into a ceiling of {{p1_ceiling_in_flight}} ÷ {{p1_w_round}} = {{p1_ceiling_rps}} requests per second. The path delivered {{p1_delivered_median}} (the median over probe 1’s steps), whatever was offered. The workers held {{p1_mean_pw}} in flight on average, {{p1_cap_share}} of the cap. The engine was not the limit. Its own latency stayed at {{p1_server50}} s while the client’s grew to {{p1_client50}} s at {{p1_step_mid}} req/s offered, so requests were waiting before the engine.

Why the workers sat at {{p1_cap_share}} of the cap, and not at the cap, is not established in this repository. The probe files record each request’s send time, finish time and the worker’s stamps. Nothing in them explains the gap. That is the open question the checkpoint asks about.

Module 3

Why GPU utilisation is blind

The usual way to read a GPU’s load is nvidia-smi, {{def:nvidia-smi}}. Its utilisation figure is {{def:utilisation}}. The harness sampled it every half second during each run and kept the median. It measures time. It does not measure how full the batch is.

An autoscaler acts when its signal reaches a threshold, which is {{def:threshold}}. The pre-registered thresholds were {{grid_util}} for utilisation and {{grid_flight}} for requests in flight per replica. A replica is {{def:replica}}. The highest utilisation threshold is {{util_top}}.

The chart puts the signals side by side as the load on one replica rises. Utilisation is measured, with a dashed line from the idle reading to the first measured level. In flight per replica is the load itself. Queue depth is {{def:queue depth}}. Past {{top_c}} the simulator keeps {{top_c}} in flight on a replica and queues the rest, so that part of the chart is the simulator’s rule and not a measurement.

What the simulator did with it

In the simulator a replica serving anything reads {{util_min}}, above every threshold in the grid. So every utilisation policy added a replica at every chance. All {{util_policies}} of them reached the cap of {{cap}} replicas, in each of the {{util_sweeps}} sweeps, and each cost the same {{cap_cost}} replica-seconds. A replica-second is {{def:replica-seconds}}. The total is one replica for the {{until}} s window, plus one more at every {{cooldown}} s cooldown from the first check at {{every}} s up to the cap, which sums to {{cap_cost_check}}.

The pre-registered iso-cost budget is the cheapest spend at which every signal has a policy, and iso-cost means {{def:iso-cost}}. For utilisation the cheapest spend is the cap, so the budget became {{cap_cost}} replica-seconds. The most expensive policy on the other two signals’ frontiers cost {{other_a}}, {{other_c}}, {{other_ra}} and {{other_rc}} replica-seconds in the four sweeps. Module 5 defines a frontier.

Module 4

Dead time and cooldowns

Adding a replica takes a cold start, which is {{def:cold start}}. Artifact 1 measured it for two setups. With nothing cached (arm A) the median was {{lag_a}} s over {{lag_a_n}} runs. With the weights on a network volume and a warm compile cache (arm C) it was {{lag_c}} s over {{lag_c_n}} runs.

That gap between asking and receiving is dead time, which is {{def:dead time}}. A cooldown is {{def:cooldown}}. While requests arrive faster than the ready replicas can serve them, they pile up as a backlog, which is {{def:backlog}}.

The spike in the artifact’s sweeps is a step. One replica’s capacity is {{sat}} requests per second, the top level of the curve, {{top_c}} in flight at {{lat128}} s each. Traffic sits at {{base_pct}}% of that, {{base}} req/s (req/s is {{def:req/s}}). The peak adds {{extra}} of a replica’s capacity, {{peak}} req/s, which is {{peak_x}} times one replica’s. It lasts {{sustain}} s. The controller checks every {{every}} s and may add one replica per decision, up to {{cap}}. One replica cannot hold that peak.

TOY · a toy for the idea, not the artifact’s simulator

Traffic is a fluid. The backlog grows at the arrival rate minus the capacity of the replicas that are ready, and shrinks when capacity is larger. One policy runs: every {{every}} s, if the backlog per ready replica is at least {{up_at}} requests, request one more replica, unless the cooldown has not run out. A requested replica becomes ready after the cold-start lag. The toy never scales down, and every replica serves {{sat}} req/s whatever the load, unlike the real curve.

Each policy ran {{reps}} times. A point on the chart is the median cost, in replica-seconds, and the median p99 over those runs.

A policy is dominated when {{def:dominated}}. The frontier is {{def:frontier}}. Comparing frontiers, and not one tuning per signal, answers the objection that a signal lost because it was mistuned. Costs within one part in a billion count as equal, since the simulator sums floating-point numbers.

Module 6

The validation gate, and why it failed

The simulator was tested before anyone was allowed to trust it. The rule was committed before any real validation run existed, because a test written after seeing the runs can be bent to fit them.

  • Three real repeats of one fixed schedule at pinned capacity. Their spread is the tolerance, since a model cannot be required to be more reproducible than the system it models. The schedule is sent open loop, which is {{def:open loop}}.
  • Bins. A bin is {{def:bin}}. Each repeat and the prediction give a p50 per bin, judged on the engine’s own latency.
  • A bin misses when all three repeats land on the same side of their own predictions by more than {{tol_ms}} ms.
  • Pass: at least {{min_bins}} judged bins, and no more than half of them missing. With {{bins_judged}} judged bins, {{allowed}} misses pass and one more fails.
  • At most two attempts: one disclosed fix, one re-validation.

A model with no error at all still misses a bin when luck puts all three repeats on one side. The rule’s authors put that chance at one in four, which is why it tolerates misses. The widget lets you see it happen.

SYNTHETIC · random numbers made in your browser, not data

This is a Monte Carlo: {{def:Monte Carlo}}. There are {{bins_judged}} bins, each with the same true p50 of {{mc_truth}} s (the mean of the calibrated repeats’ p50s). Each of three repeats is the truth × (1 + spread × a random number from a bell curve). The model predicts the truth × the host factor, so a factor of 1.00 is a model with the right speed. A bin misses when all three repeats are more than {{tol_ms}} ms above the prediction, or all three are more than {{tol_ms}} ms below it.

Default {{spread_default}}%. It is the median, over bins, of the spread of the calibrated repeats’ residuals, as a share of {{mc_truth}} s. It is an estimate and may overstate the real spread.

Each column is one bin. The three dots are the repeats relative to the prediction, in milliseconds, on a scale that is linear within ±{{tol_ms}} ms and logarithmic beyond. The band is the {{tol_ms}} ms margin. Shaded columns missed.

At spread {{spread_default}}% the {{tol_ms}} ms margin is a real share of the repeats’ scatter, which puts some bins out of reach of a miss, so a perfect model misses about {{mc_perfect}}% of bins and not a quarter. Raise the spread and that approaches the one in four. At the default spread, a host factor off by a few percent puts all three repeats on one side of the prediction in nearly every bin.

The real result

Attempt one judged the simulator with the committed curve as measured. Attempt two first scaled the curve by two ratios measured on the worker just before the replay: its latency over the curve’s at {{cal_lo}} and at {{cal_hi}} requests in flight, each from a closed-loop hold. Both attempts failed. The residual is {{def:residual}}, per repeat per bin.
