Module 1

A swap is a cold start minus the expensive parts

12 min

A swap stops the vLLM server for one model and starts it for another, on the same GPU in the same container. Artifact 1 measured a cold start: a new host, platform scheduling, the weight download, engine start, the health check and a first token. A swap runs on a host that is already up, so some of those lines of the bill are never sent.

The model here is Qwen3-1.7B, with 16 measured swaps, all warm: the weights sit in the page cache and the compile cache holds the compiled graphs. The median swap takes s.

Where the time goes

Medians. The cold start is artifact 1's arm C (weights on the network volume, warm compile cache) for an 8B model, so it is a reference bar. The models differ, so no stage of one is subtracted from the other.

The swap's six stages

StageMedianWhat happens

What a swap skips. Platform scheduling ( s in the cold start) and the weight download ( s of the s). Compilation is skipped too, because the compile cache is warm. What it still pays is the process restart: interpreter start, importing the libraries and waiting for the server to report healthy. That is s of the s. For a model this small, a swap takes about as long as artifact 1's 8B cold start.

Sleep mode avoids the process restart: the engine goes to sleep and wakes. The median switch was s over repeats. It is reported next to the crossover and never inside it, because the host memory a sleeping model holds was not measured, so the simulator cannot price it.

Checkpoint

From the table, say which stages a swap pays and which it skips. Say why a 1.7B swap takes about as long as an 8B cold start even though it skips so much. Then say why the 8B bar is a reference and not a baseline, and what sleep mode avoids and what the post says it cannot price.

What a passing answer contains

Paid: teardown, memory release, the process restart (interpreter, imports, health), weight load from page cache, the rest of engine init. Skipped: platform scheduling, the download from the volume, first-token latency in this accounting, and compilation (a cache hit costs 0.3 s). The restart dominates, so shrinking the model shrinks only the weight and init stages, which were never the large part. The 8B bar has a different model, so no stage of it can be subtracted from a stage of the swap. Sleep mode avoids the restart; its unpriced cost is the host memory the sleeping model holds.

Follow-up to expect: "So would a bigger model swap slower?" Weight load and engine init would grow; the restart would not. Only the first was measured, on one size.

Module 3

Zipf, locality and the two regimes

15 min

Zipf skew says how uneven the traffic is across models. Rank the twenty models by popularity: the model at rank k gets a share proportional to 1 ÷ ks. At s = 0 every model is equal. As s grows, the first few models take most of the requests.

Twenty models at skew s

Frequency is not locality. Two workloads can send each model the same share of requests and still behave differently for a cache. The simulator draws two kinds of arrival, with the same long-run rate per model:

  • Spread. Poisson arrivals, each labelled with a model independently. A model's requests are spread across the whole window, with no memory of which model came before.
  • Bursty. Each model alternates between ON periods (mean 120 s, ON a fifth of the time) and OFF periods, with Poisson arrivals while ON. Its requests come in bursts with long gaps.

For swapping, which is a cache of models on GPUs managed by least-recently-used eviction, that difference decides everything. A bursty model is loaded once and serves a burst. A spread model is evicted before its next request arrives. LRU is held fixed and not compared, so the strategy is judged on the traffic it gets, not on a better policy.

Checkpoint

What a passing answer contains

Skew is the concentration of requests on a few models: at s = 1 the top model has about 28% of the traffic and the last about 1.4%. Swapping works while a model is still resident when its next request comes. Bursty traffic gives that; spread traffic does not, so the pool thrashes: every request finds its model absent and evicts another model that will be needed soon. The post says it did not diagnose why the spread swap fleet needs more GPUs at s = 1.25 than at s = 0.6.

Follow-up to expect: "Why isn't LRU compared with something smarter?" Because the question is the placement strategy under one fixed policy. A predictive policy is a limit the post states, not a result.

Module 4

Averages hide tenants

12 min

The obvious way to size a swap fleet is the smallest one whose aggregate p99, over all requests, meets the SLO of s. With Zipf traffic the popular models send most requests, so the aggregate is largely their p99. The pre-registered rule is stricter: the smallest fleet where every popularity decile meets the SLO. At the reference point (bursty, s = 1.0), the two rules disagree by one GPU.

What a passing answer contains

The aggregate p99 is dominated by the hot models' requests, so it can meet the SLO while a hot decile does not. At 9 GPUs the two hottest deciles have p99s of about 87.7 s and 77.2 s against the SLO of 75.6 s, and the coldest meets it. The expected failure, cold tenants suffering because their models are evicted most, did not appear at this point; the post says it has not measured why. A fleet that is cheaper only because it breaks the SLO for some tenants is not cheaper at the same service, so the comparison is made at the fleet that meets the SLO for every decile.

Follow-up to expect: "Is one GPU a big difference?" At the reference rate, 730 hours a month, one GPU is about $810 a month, so about $40 per tenant per month across twenty tenants.

How much interference could co-locating survive?

The interference grid has no neighbour between 0 and 16, and the simulator interpolates there. This exploratory run re-sized the reference skew with the penalty changed: step charges any busy neighbour what 16 costs, and x4 and x8 multiply every busy-neighbour latency.

Why the rule depends on the SLO

The SLO is 2 times the median swap, s. It was chosen by a pre-registered screen before the campaigns, applies to all three strategies, and favours swapping, because a swap fleet needs an SLO loose enough to absorb a swap. Co-located latency is about 3 to 6 s against that SLO, which is why the co-located fleet barely reacts to the interference surface. A tighter SLO could remove swapping's advantage. It was swept only over the screen's three multiples of the swap median.

Dedicating needs 21 to 25 GPUs for twenty models in the bursty regime. That is more than one per model because the hot-model rule gives a model whose load in a burst exceeds 0.7 of a GPU as many GPUs as keep each below that.

Checkpoint

Check your module 0 prediction. State the rule, and say why there is no crossover along skew. Then say what the 75.6 s SLO does to the answer, and use the interference run: at what multiple of the measured penalty does co-locating stop winning, in which regime first, and why that run is exploratory.

What a passing answer contains

Spread arrivals: co-locate at every swept skew (10 GPUs, the floor of its search). Bursty arrivals: swap at every evaluable skew from 0.8 to 2.0; at 0.6 the bursty regime has a decile too thin to compute a p99 and the pre-registered rule is to publish no number. Along the skew axis the estimator finds no crossover in either regime; the winner changes between the regimes. The SLO is loose enough to absorb a swap and to hide the interference. Multiplying the busy-neighbour latency by 4 leaves the spread fleet one GPU short of losing to swapping (12 against 13), and by 8 it loses (16 against 13); in the bursty regime co-locating loses to swapping at 4. The run is exploratory: one skew, 6 repetitions, run after the analysis, and the multipliers are not measurements.

Follow-up to expect: "So is co-locating safe in the spread regime?" It has room of a factor between 4 and 8 on the interference, at this SLO, and the validation gate never exercised it. That is module 6.

Module 6

The validation gate, and why it failed

25 min

The simulator was to be trusted only after it reproduced a real replay under a test written before the data. The gate: three tenants of the measured model on one GPU, a 900 s bursty trace of requests, replayed three times for real. The simulator replays the same trace. Its median latency in each 30 s bin must fall inside the band of the three real repeats, widened by 0.001 s. At most half the judged bins may miss, and the predicted swap count must be within one of the real repeats' range.

It failed: of judged bins agreed, so 10 missed, the largest by s, always with the simulator predicting the engine slower than it was. The swap count agreed: predicted , real in all three repeats.

What the swap charge does to the miss

The gate charged each swap the swap campaign's median, s. The swaps inside the replays took about , and s, on a different pod. Choose a charge and see how many bins agree (exploratory re-runs of the prediction).

A uniform host-speed difference of up to 30% on the solo curve did not close the miss either. No fixed charge gets close to passing.

Each repeat held to its own swap time

With the swap cost the repeats actually paid, the simulator predicts latency lower than the engine's in almost every bin. So no single fixed swap cost matches the real system: about 38 s over-predicts and about 25 s under-predicts. The simulator charges a swap as a fixed stall of the whole pool. Something in a real swap costs a request more than the swap's start-to-ready time, and the model has no term for it. Requests drained from the old engine and the first requests on a fresh engine being slower are candidates; none was measured.

What the gate did not cover. It replays one GPU with the swap strategy and the solo curve. Co-location has no replay; its check is two held-out interference cells, of which passed (pair:o24:n48 passed; pair:o48:n24 predicted 13.8 s against a real median of 16.5 s). The gate's bursts are 180 s at a duty of 0.25, offered at 0.3 of one GPU's saturation, where the sweep's are 120 s at 0.2.

Checkpoint

State the gate and the verdict. Explain how a swap charge of 37.8 s against about 25 s puts every miss on one side, and why charging each repeat its own swap time still fails with the sign flipped. Say what the gate did not cover. Last, propose the measurement that would say how much of the failure is the host and how much is the model, and say why a calibrated re-run would not rescue the result.

What a passing answer contains

Gate: three repeats, a band widened by 0.001 s, at most half the bins missing, swap count within one; verdict failed, 10 of 13 bins. Charging 37.8 s for swaps that cost about 25 s adds about 12 s ten times in a regime where bursts offer about 1.2 times what one GPU can serve, so the error accumulates as queue delay and every miss is the simulator being slower. Charged the true swap time per repeat, the simulator under-predicts, so the missing piece is a cost the model does not have. The gate did not exercise co-location, and its trace is not the swept bursty regime. The measurement: a swap's effect on the requests in flight and just after it, on one pod, with the replay's own requests. A calibrated re-validation would fail too (12 of 13 bins), so it would not rescue the frontiers; the verdict stands as the registered gate produced it.

Follow-up to expect: "Why not just tune the swap cost until it passes?" Because no value passes, and a gate tuned after the data it judges would no longer be the registered one.

Module 7

What could not be concluded

8 min

The post's Limits section lists what the result does not cover. The ones that matter most come from the failed gate:

  • The validation failed, so the decision rule is a simulator's. The GPU counts are validated nowhere: the gate failed at the one point it tested, one GPU with three tenants and swapping only, while the fleets are 10 to 25 GPUs. Co-location has two held-out cells and no replay.
  • A small-model regime. Qwen3-1.7B, not the pre-registered Qwen3-4B, which failed the co-residency go/no-go.
  • Homogeneous sizes, LRU only, one GPU class in one datacenter, and one pod measured most of the curve.
  • Warm swaps only. The page-cache eviction tried dropped less than the registered rule required, so cold swaps are not reported.
  • Rare request rejections. A few runs failed because one request was rejected; the cause was not established.
  • The SLO is 2 times the median swap and favours swapping.

Name three limits the post states about itself, and say which one makes the others matter most. Then say what separates an amendment made before the data it governs from a forking path, using the order in the table.

What a passing answer contains

Any three of the limits above. The failed validation makes the others matter most: without a validated simulator, every extrapolation beyond one GPU with three tenants rests on the model alone. An amendment is made, dated and signed off before the data it governs is analysed, with the reason recorded (the KV pin followed an out-of-memory failure, the validity rule followed a rule that could never be met above capacity), and the commit order proves it. A forking path chooses the rule after seeing which result it produces. Two things still stay discounted: the amendments changed what counts as a valid cell, and the re-runs they caused were large (44 cell runs).

Follow-up to expect: "Couldn't the amendments have been chosen to favour a result?" They were made on validity grounds, before analysis, and the validation outcome they preceded went against the author's model.
