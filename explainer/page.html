Where a cold start goes

A cold start is the wait while a machine boots and loads a model, before anyone gets an answer. Arm C's median cold start is {{median_t_total_C}} seconds, against {{median_t_total_A}} with nothing cached.

{{spine}}

Beat 1 · the schedule

Run 147 is arm B, and it was arm B before the campaign started. The scheduler draws the whole order once, from a seed: {{runs_total}} runs as randomised triples, one of each arm in every triple, shuffled within it.

Running all of arm A, then all of arm B, then all of arm C would have been simpler and worthless. A rented GPU at 3am is not the same machine as one at noon — different neighbours, different network, different luck of the draw on which host you land. Blocking hands that drift to whichever arm happened to run through it. Interleaving spreads it across all three.

Beat 2 · preflight

Before any money moves, preflight fetches the live endpoint from RunPod's API and compares it, field by field, against a dict of pinned values: platform snapshotting off, this GPU type, this network volume, this container template. One difference and the campaign does not start.

The guard exists because the failure it catches is invisible afterwards. An endpoint with the platform's own boot-acceleration switched back on returns a complete, plausible, entirely wrong dataset — it measures RunPod's cache instead of the three arms, and nothing in the numbers says so.

Beat 3 · submit

The submitter stamps the job with its two facts — {arm, run_id} — and posts it.

Clock A starts here. It is the laptop's stopwatch: submit to result, queueing and scheduling and network included. It is the only one of the three clocks that sees the wait before a container exists, and therefore the only one measuring what a user would actually feel.

Beat 4 · the platform

RunPod accepts the job, queues it, finds a free 4090, and boots the container image onto it. You are comfortable with this part already: it is a cold start in the ordinary serverless sense, the one you avoid in production by keeping a worker warm. Here it is the thing under the microscope, so nothing is kept warm on purpose.

Clock C is the platform's own account of that stretch, and it is an odd instrument: it reports durations — how long the job waited, how long it ran — and never timestamps. There is no instant to line up against clock A. Only two lengths that ought to add up.

Beat 5 · the handler prepares

Inside the container, the handler turns arm B's configuration into two environment variables, creates the directories it is allowed to create, and refuses outright if a path claims to be on the network volume and the volume is not mounted — silently landing that cache on container disk would make arms B and C run cold while reporting themselves warm.

Then, before starting anything, it records whether this arm's compile cache directory already exists. The ordering is the entire point. Why that ordering matters is card 4's lesson — for now, just note that the snapshot happens first, and that moving it later would look like a tidy-up.

Beat 6 · the probe starts the engine

The probe launches vllm serve as a subprocess and hands its stdout to a thread that reads line by line, forever.

Clock B starts at that instant. A monotonic stopwatch inside the box, in the same process as the thing it times, with no network between the clock and the event. That is why clock B can name phase boundaries to the millisecond while clock A can only bracket the whole run — and why the two are never added together.

Beat 7 · vLLM does four things

Load the weights. Compile the model. Size the cache that holds conversations. Capture the GPU call sequences. None of that is this repo's code, and the probe never patches the engine to find out where it is — it reads the log lines vLLM already prints about itself and promotes two of them to marks.

This is where the bulk of a cold start lives: with nothing cached, the median run takes {{median_t_total_A}} seconds, and the tail reaches {{p95_t_total_A}}. The section below this diagram opens the box.

Beat 8 · ten requests

The health endpoint answers, so the engine now calls itself ready. Ten requests go in anyway, one after another, each one timed on clock B.

The engine is warm by any reasonable definition, and we time it warm on purpose. The question is whether “ready” and “fast” are the same moment — whether a replica that has just announced itself is fit to take traffic, or whether the first few users quietly pay for the rest.

Beat 9 · the result channel

The probe hands the entire bundle back as the job's result — the JSON RunPod returns to the submitter — and not as log output.

Logs are a lossy channel. They truncate, they interleave two workers' lines, they arrive late or not at all, and a run whose only telemetry lived in stdout is a run you paid for and cannot use. A result either comes back whole or fails loudly enough to retry.

Beat 10 · nothing is judged yet

The row is written whether the run succeeded, failed its health check, timed out, or came back internally contradictory. Raw fields, no verdict.

Validity is decided later, offline, by code that can be re-run against the same file as many times as you like. Judging at write time inverts that: a bug in the judge no longer produces a wrong answer you can find and fix, it produces no data — the evidence that would have exposed the bug was discarded by the bug.

One run in this campaign took {{first_touch_seconds}} seconds, because it was the first time that model had ever been pulled to that region. It is in the file. It is labelled, and excluded downstream by a rule written in advance. It was never deleted.

Beat 11 · one row appended

A single line of JSON, appended to the campaign file. Self-describing: every field the analysis needs is named in the row itself, so the file still means something without the code that wrote it.

Append-only carries more weight than it sounds like. A {{runs_total}}-run campaign spans hours of paid GPU time; workers recycle, laptops sleep, the first attempt died of a full disk. The only recovery that actually works is “stop, then start again after the last row on disk.”

Beat 12 · offline, no GPU

Everything from here runs on a laptop and touches nothing but that file. The three clocks are reconciled against each other; runs that break the rules fixed in advance are discarded with a named reason rather than quietly repaired; per-phase durations are derived; ranges are computed by resampling the measurements; the charts are drawn.

The medians land at {{median_t_total_A}} seconds with nothing cached, {{median_t_total_B}} with the weights already on the volume, and {{median_t_total_C}} with the compiled artifacts there too.

Every number published anywhere about this experiment comes out of this stage — not out of a notebook someone ran once. That is the point of pushing the whole judgement downstream: clone the repo, run the pipeline, and you re-derive all of it, including the numbers in this sentence, without renting anything.

Zone 4 — what is actually in the box

Everything above treats vLLM as a box that takes eighty-odd seconds to open. It is worth knowing what it is, because two of its four startup steps are the entire experiment.

What it replaces

The obvious way to serve a model is a loop: read a request, call model.generate(), write the answer back, read the next request. That works, and it is what every tutorial shows. It also holds one conversation at a time, leaves the GPU idle between a user's tokens, and gives you no way to serve two people at once short of loading the weights twice.

What it is

An HTTP server wrapped around the model. This repo starts it as a subprocess — literally vllm serve <model> --port 8000 — polls http://127.0.0.1:8000/health until it answers, and then sends its warmup traffic to /v1/completions. That is the whole interface the probe needs: a process, a port, a health route, and an OpenAI-shaped completions route.

What you get for it is one copy of the weights with many users' requests multiplexed over it. That is continuous batching — serving many users' requests through one copy of the model at once — and requests join and leave the running batch between decode steps rather than waiting for a batch to fill. It is also why a fresh replica is useful the moment it reports ready: it does not need traffic to warm itself into efficiency. It needs memory.

What it is not

Not a model. The weights are a separate download, pinned to a revision, and vLLM will happily serve a different one. Not a trainer — nothing in it computes a gradient. It is a scheduler and a memory manager with an HTTP front door.

Why starting it costs real time

  • Load the weights. Roughly 15 GB moved off disk, or off the network volume, into HBM — the GPU's own memory, separate from the computer's RAM. This is the step arms B and C shorten by having the file already staged on the volume.
  • Compile the model. torch.compile — a step that turns the model into faster GPU code before serving — traces the model and generates kernels for it. Slow once; reusable afterwards if the output is kept. Keeping it is the only thing arm C has that arm B does not.
  • Size the cache that holds conversations. Measured, not configured. See below — this is where the interesting failure is.
  • Capture the GPU call sequences. CUDA graph capture — recording a fixed sequence of GPU operations so they replay without per-step overhead — costs a flat four seconds here, identical in all three arms because it depends on the shapes captured rather than on anything cached, and pays itself back on every token afterwards.

The consequence you already have the parts for

You can already list what sits in GPU memory beside the weights: activations, and the K/Q/V matrices. One correction is owed. Q is not kept — it is computed fresh for the token being generated and thrown away. Only K and V are retained, which is why it is called the KV cache and not the QKV cache: per-conversation scratch space the model keeps on the GPU while generating. It grows by a slice per token, and every slice stays until the conversation ends.

Now finish the chain, because this is the part that bites. The card holds 24 GB. The weights take ~15 GB and never move. What remains, after activations and working space, is the entire budget for every conversation the replica will ever hold simultaneously. Context length multiplied by concurrent conversations is a hard ceiling — and vLLM computes that ceiling once, during startup, and never revisits it. The replica you boot at second zero has a fixed conversational capacity for its whole life.

The dividend: a compile cache buys capacity, not just seconds

How does vLLM decide how much memory the cache gets? It cannot ask. No API reports “free memory for a KV cache.” The only way to find out is to run the model once on the largest batch it must support — a forward pass, running the model once, start to finish, on some input — record peak usage, and hand the remainder to the cache.

On a cold-compile arm, the compiler's own working set is still resident while that measurement runs. The profiler is not wrong; it accurately reports less free memory than the replica will have a second later. vLLM sizes the cache to what it saw: {{kv_cold}} tokens instead of {{kv_warm}}. At the context length held fixed across all three arms, that is {{concurrency_cold}} concurrent conversations instead of {{concurrency_warm}} — one whole request of capacity, on the same card, for the life of that replica. Nothing later reclaims it.

The instrumentation point

vLLM was never modified, forked, or monkey-patched to produce any of this. The phase boundaries come from lines the engine already prints about itself, matched by pattern against real captured logs held as fixtures.

That is the transferable trick, and the code below shows the half of it that is easy to miss: most of those comments are about the lines that were rejected. There is a plausible-looking line a few entries earlier that reports the weight loader finishing, and another pair a few entries later that report the HTTP server binding. Matching either would shift a boundary by seconds and produce a clean, confident, wrong number. Choosing a marker in a black box is mostly choosing which neighbour you refuse.

Six pieces of code worth reading

Each one is small, and each one exists because of a specific way this experiment could have produced confident nonsense.

Card 1 — a guard that refuses to check nothing

coldstart/preflight.py

What it is
A dict of pinned endpoint settings, and a function comparing the live endpoint against it.
Its one job
Refuse to open a paid run window if the endpoint has drifted from the configuration the experiment was designed around.
Why it exists
A safety check that cannot do its job must fail, not shrug. Handed an empty pin set, the natural implementation iterates zero times, finds no mismatches, and reports success — on any endpoint at all, which is precisely the false pass the module exists to prevent. So it raises instead. The same instinct one line further down: a key missing from the endpoint response counts as a mismatch, not as “probably still fine.”
Hands off to
The driver, which submits nothing until this returns.

Card 2 — the one thing that differs between arms

coldstart/cache_config.py

What it is
The three arms as one frozen object with two fields, and a method that turns them into exactly two environment variables. Same image, same entrypoint, same engine flags; one swapped object.
Its one job
Express the experiment's single independent variable in a form the container can consume, and nowhere else.
Why it exists
Warm paths deliberately point at a shared location on the network volume — the whole meaning of warm is that a later run finds what an earlier run left. Cold paths are the opposite, and so they are namespaced by the run id. A serverless worker outlives any single run. Without the namespace, the next run's “cold” arm starts up, finds the previous run's downloaded weights already sitting on local disk, and reports a cold start that never happened — as a perfectly plausible number, in the arm whose whole purpose is to be slow.

Card 4 — the line that must not move

worker/handler.py

What it is
One directory check, under a comment roughly fifteen times its length.
Its one job
Answer “was this arm's compile cache already there when the run started?” — which is a question about a moment, not about a directory.
Why it exists
A directory check cannot tell “found a pre-existing cache” apart from “just created one by compiling.” A cold compile creates that directory as a side effect of finishing. So the identical call, moved a few lines later to sit with the other post-run bookkeeping, still returns a boolean — it just answers a different question. It would report a warm cache for every genuinely cold run, and the downstream arm-state gate would then discard roughly 200 of the {{runs_total}} paid runs as inconsistent. In the other direction it goes blind: an actual warm cache leaking onto a cold arm, the exact contamination this check exists to catch, reads exactly the same as the bug. This is what a correctness bug disguised as a simplification looks like: nothing crashes, nothing looks wrong, and two thirds of a campaign evaporates.
Hands off to
The record, and from there the offline gate that compares the observed cache state against the arm the run was supposed to be.

Card 5 — when three clocks disagree

coldstart/checks.py

What it is
The rule that decides whether clock A and clock B can both be telling the truth about the same run.
Its one job
Detect the impossible and name it, without repairing anything.
Why it exists
Clock A ran on a laptop; clock B ran in a datacentre in another country. A contains B by construction, plus queueing, plus two network crossings. Their difference is the only cross-clock subtraction this codebase permits at all. If that difference comes out negative, something is badly wrong and the run raises rather than being clamped to zero. If it comes out positive but smaller than 50 ms — less than one honest round trip between those two machines — then the two clocks are not disagreeing slightly, they are describing events that cannot both have happened, and the run is discarded with a named reason recorded beside it. A rule fixed in advance, applied by code, leaves an audit trail; an eyeball applied to a scatter plot does not.
Hands off to
The caller, deliberately: this function decides nothing about storage, so a discard is always something someone chose to record.

Part II — how to read a number somebody hands you

Part one of this page was one experiment, walked end to end, and it is the less useful half. The useful half is a habit you can carry to the next benchmark you are shown: the vendor chart, the framework's README, the internal dashboard announcing that the regression is fixed.

Four questions. Each one has a story here, and each story is a place this experiment either held up or got caught.

Act 1 — “81 seconds” is not a finding

Arm A's median cold start is {{median_t_total_A}} seconds. Written on a slide by itself, that is not a measurement. It is a measurement with the measurement removed. It does not say how many runs went into it, and it does not say what they looked like.

So look at them. Below is an ECDF — a chart showing what share of runs finished by each time. Pick a height on the left, slide right until you hit a line, read the seconds off the bottom.

Arm A's line does not climb. It steps, goes flat for four and a half seconds with nothing whatsoever in it, and steps again. About half the runs finish just past eighty seconds; most of the rest arrive in a second bunch near eighty-six; a thin tail runs out to the 95th percentile — the value below which a given share of measurements fall — at {{p95_t_total_A}} seconds.

There is no such thing as arm A's cold start time. There are two of them, and a tail. Any single number pulled out of that — median, mean, best-of-five — names one behaviour and buries the other. The mean, in particular, lands in the four-and-a-half-second gap: a time that not one of the ninety-nine runs took.

Question one: how many runs, and what was the spread? A claim with no n behind it is a claim somebody ran once. A claim with an n but no shape behind it can still be two different behaviours wearing a single number as a hat.

The interlude — what an interval is, and what it is not

Question one has a second half that almost everyone, including the author of this page, gets wrong on the first three attempts. It is worth the detour, because the wrong version is confident, sounds right, and survives being told the correct definition.

Pin the sample first

Arm A alone, and ninety-nine of its hundred runs. The hundredth is the first-touch run at {{first_touch_seconds}} seconds, held out by the rule from beat 12. That is worth noticing on its own: the gate is not decoration, it is the reason the other ninety-nine are a single population and not ninety-nine runs plus a category error.

Refute the wrong reading with its own data

Over those ninety-nine runs, the interval on arm A's median is {{arm_a_ci_n99}} seconds. Almost every reader takes that bracket to mean this is where most of the runs landed — a bell-ish pile of measurements, the bulk of them inside the brackets.

It cannot mean that. Look back at the chart. The bracket spans 82 to 85 seconds, and not one of the ninety-nine runs is in there. It also stops short of the nine runs bunched at {{p95_t_total_A}} seconds, which are as real as any others. A range that covers a stretch holding nothing, and excludes a stretch holding nine measurements, is not a description of where the measurements are. Whatever it describes, it is not that.

Shrink it until the machinery is visible

Ninety-nine numbers is too many to watch. Suppose the whole experiment had been five runs: 80, 80, 81, 85, 86. The median is 81.

Write those five on slips of paper and drop them in a bag. Pull one out, write it down, put it back, pull again — five pulls, because the campaign had five runs. You might get 80, 85, 80, 80, 86, whose median is 80. Do it again: 86, 81, 85, 85, 80, median 85. Again: 80, 80, 80, 81, 85, median 80.

None of those is invented data. Each one is an imaginary campaign built only out of numbers this experiment actually produced — a plausible alternative afternoon. And each one hands back a single median. Run ten thousand imaginary campaigns, collect the ten thousand medians, sort them, and cut off the extreme 2.5% at each end. What is left is the bracket.

That is a bootstrap interval — a range showing how much a summary number could move if the measurements had come out slightly differently. It is an answer to “how firmly is the median pinned,” and it answers nothing at all about where individual runs land. The chart above already answered that.

The word that does the damage

People describe this as shuffling the data, and that word is a large part of why the wrong reading is so hard to dislodge. Shuffling is reordering. Reordering cannot move a median by a picosecond — put ninety-nine numbers in any order you like, sort them, and the middle one is the same number every time. If shuffling were what happened, every imaginary campaign would return an identical median and the bracket would have zero width.

The operation is drawing with replacement — picking a value, writing it down, putting it back, and picking again. The putting-back is the entire mechanism. It is what allows one run to turn up three times in an imaginary campaign while another turns up not at all, and that lopsidedness is the only reason two imaginary campaigns ever disagree.

Break the wrong model on purpose

If you still half-suspect the interval is measuring the gap between arm A's two clusters, that is a reasonable suspicion and arm A cannot talk you out of it. Its interval runs from about 81 to about 86, which is precisely where its two clusters sit. The two readings make the same prediction on this data. So change one thing, and only one.

Take ninety-nine imaginary runs with only two distinct values in them: 81 seconds and 86 seconds, nothing between. Split them 51 to 48, and the interval comes back [81.00, 86.00]. Five seconds wide. That certainly looks like the gap.

Now split the same two values 70 to 29. Same two clusters, same five seconds between them, same spread in the measurements. The interval is [81.00, 81.00]. Zero seconds wide.

The gap never moved, so the gap was never what was being measured. What moved is how easily a re-draw can shove the middle value across to the other cluster. At 51 to 48 the median is balanced on a knife edge and one unlucky bag tips it; at 70 to 29 it is not close, and all ten thousand imaginary campaigns come back 81. A zero-width interval does not mean the runs were identical. It means the median was never in doubt.

What the interval cost, and what it did not

Two very different kinds of expense go into that bracket, and keeping them apart is the last piece.

The ninety-nine runs cost {{gpu_hours_a_n99}} GPU-hours on a rented card, paid for in real money, and they alone set the width. The ten thousand resamples cost nothing: a fraction of a second on a laptop, no network, no GPU, and past a few thousand of them the answer stops moving in any digit anybody publishes.

So the resampling adds no information. It reads back what the ninety-nine runs already implied, to more decimal places than the ninety-nine runs deserve. If a bracket is too wide to support the claim you want to make, there is exactly one lever, and it is the expensive one.

Act 2 — decided before, or decided after?

Return to the first-touch run: {{first_touch_seconds}} seconds, twenty-odd times its own arm's median, one observation out of {{runs_total}}. Excluding it is obviously the right call. It is also, from the outside, completely indistinguishable from the most common way a benchmark lies — run it, dislike a number, find a reason the number does not count.

The defence is pre-registration — writing down what counts as a result before looking at the data. This experiment has one, committed four days ahead of the first run: every hypothesis, both contrasts, the exclusion rules, the stopping rule, and the rule for picking which finding leads.

The rule that excludes that run was not in it.

It was committed roughly half an hour after the first window's data landed, because that window contained a run large enough to make the pooled chart unreadable. The artifact says so in its own write-up, in as many words: that is a post-hoc analysis decision, and calling it anything else would be the exact failure the whole thing was built to avoid.

Two things keep it from being a fudge, and both are worth stealing. First, the criterion is mechanical rather than a judgement about that particular run: a run is first-touch when it is the first ever seen on its host id, derived from the file and applied backwards across all {{runs_total}} rows. It excludes nothing for being large. Had the slowest run of the campaign been a repeat-host run, it would still be in the chart. Second, the amendment is dated in git, so the ordering is checkable rather than asserted.

Question two: was that decided before you looked? Hardly any benchmark you are shown can answer it. One that can — and that names the place where it failed to — is telling you something the spotless ones structurally cannot.

Act 3 — compared to what?

{{median_t_total_C}} seconds is not fast. It is not slow either. It is not anything, because fast is a comparison, and a comparison is only worth reading when the two sides differ in exactly one way. That is what card 2 is for: same image, same entrypoint, same engine flags, same model revision, one swapped configuration object. Everything else is held down so that the difference has only one place to come from.

Two comparisons come out of that, and each is a contrast — the difference between two arms, measured on the same quantity. A to B, which adds weights already staged on the volume, is {{contrast_ab_total}} seconds on total time. B to C, which adds the compile cache on top, is {{contrast_bc_total}}.

Now the question that separates the people who compute from the people who eyeball: is the compile cache worth more than the staged weights? That is a difference between two differences, and the temptation is obvious. The brackets are printed right there. Subtract the ends and be done.

On this data, that works. The honest figure, resampled across both contrasts on the same runs at once, is {{difference_of_contrasts}} seconds — and naive end-to-end subtraction lands within 0.04 s of both ends of it. The shortcut is right here. An explainer that showed you this data while claiming the shortcut had failed would be lying to make a point.

The lower panel is what happens when the two estimates share a source of error — the same host, the same window, the same noisy neighbour pushing both measurements the same direction. That shared push cancels when the difference is computed run by run on paired data, and does not cancel when you subtract two summaries. The naive bracket comes out several times too wide, which is not a harmless conservatism: it straddles zero and hides an effect that is really there.

So the lesson is not “never subtract endpoints.” It is narrower and much more useful: nothing visible in the two intervals tells you which of those two panels you are in. The brackets look the same in both. The correlation is not recoverable from the summaries, only from the paired runs underneath them — which is why the difference is computed rather than derived, and why an experiment that only publishes summary intervals has quietly made this uncheckable.

Question three: compared to what, and where is the interval? A speedup with no baseline is a press release. A difference of two differences quoted without its own interval is arithmetic somebody did in their head.

Act 4 — what could this not tell you?

Five hypotheses were registered before the campaign began. One of them was about host placement: whether the machine you happen to land on drives the tail harder than any cache does. It is a good hypothesis, and probably the most commercially interesting of the five. This experiment cannot answer it.

All {{runs_total}} runs landed on the same machine. {{hosts_observed}} host, three hundred runs. RunPod kept re-allocating the box that already had the image, and no endpoint setting changes that for a driver submitting one job at a time.

Read what that chart does rather than what it shows. It could have been a single bar drawn to scale, captioned “median by host” — technically true, and it would have started travelling as evidence about host variation the moment somebody screenshotted it away from its caption. Instead it writes NOT ANSWERABLE across its own title, because a figure has to survive being separated from the page it was born on.

There is a consolation, and it is stated as one rather than as a save: because every triple ran on one host, host effects are held constant instead of confounded, so the paired comparison in act 3 is cleanly supplied. The design lost a hypothesis and got back a control it had not asked for. That trade is still a loss, and the write-up reports it under a heading that says so.

Question four: what did this fail to show? Almost nothing you are handed answers it. Work that names its own dead hypothesis is telling you the author went looking for the places it breaks — which is the only evidence you will ever get that the numbers that did survive were treated the same way.

The card

Four questions. They cost about ten seconds to ask, they work on a vendor chart and on your own pull request, and the ones that go unanswered tell you more than the ones that do.

Four questions for any performance claim

  1. How many runs, and what was the spread? One run is an anecdote. A single number over a two-humped distribution is a time that nothing actually took.
  2. Was that decided before you looked? Exclusions, metric, and headline all have to predate the data — otherwise the data picked them.
  3. Compared to what, and where is the interval? Fast is a comparison against something that differed in one way. A difference of two differences is computed, never eyeballed.
  4. What did this fail to show? A dead hypothesis, named out loud, is the rarest signal there is.

An interval says how firmly the summary is pinned, not where the runs landed. Those are different charts.

The experiment above is worth about what any single campaign is worth: one provider, one GPU, one model, one region, one host. The seconds do not transfer anywhere. The four questions do, and they are cheaper than renting anything.
