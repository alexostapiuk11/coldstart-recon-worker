Module 1

What an adapter is, and what rank sets

10 min

Fine-tuning a model normally changes every weight, which gives you a whole new model. LoRA leaves the original weights frozen and trains a small pair of matrices that are added next to selected layers. What you keep is the pair: an adapter of megabytes, not a model of gigabytes. One base model can then host many adapters.

The pair is small because it is low-rank. A weight matrix of shape din × dout gets two factors, din × r and r × dout, where r is the rank. The rank is the size knob. This artifact fixes it at 16 and puts the pair on seven projections in every layer: q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj.

Why the values inside the adapter do not change the cost

The work an adapter adds is set by shapes, not by values. vLLM runs the kernel at the buffer rank (max_lora_rank), so every adapter in a slot is a 16-wide pair on the same seven projections. A dense matrix multiplication does the same arithmetic and reads the same bytes whatever numbers sit in it.

The one route from weights to serving cost is what they make the model generate. Here that route is shut: every request is forced to produce exactly 16 output tokens (ignore-EOS), and prefix caching is off. So random adapters measure the serving cost of any rank-16 adapter on this base model.

What this licenses and what it does not. It licenses claims about serving cost for rank 16, these seven projections and this base. It licenses nothing about output quality, and nothing about other ranks. The argument is only an argument until the equivalence gate (module 5) checks it.

Checkpoint

Say why an adapter is megabytes beside a model of gigabytes, why serving cost depends on shapes and not on values, and what that licenses and does not license.

What a passing answer contains

The adapter is two thin factors per targeted projection, r × (din + dout) numbers against din × dout. Cost depends on shapes because the kernel does the same multiplications at the same rank for any values. The weights could only matter through what the model generates, and fixed 16-token outputs with prefix caching off shut that route. Licensed: serving cost at rank 16 on this base. Not licensed: quality, other ranks, other models.

Follow-up to expect: "What would make that reasoning invalid?" Answer: anything that lets values change work, such as outputs of different length, or a cache that hits for one adapter's prompts and not another's.

Module 2

Registered is not active

15 min

In vLLM 0.27.1 one setting, max_loras, is two things at once. It is the number of GPU slots: weight buffers are allocated per slot, whether or not an adapter occupies it. And it is the cap on distinct adapters in one batch. Every sweep point here sets max_loras = max_cpu_loras = N, so every registered adapter is resident in a slot.

That means the configuration cannot separate registered from active. Traffic does it instead. The load generator runs two regimes on the same server:

  • Concentrated. Every request names the same one adapter. One adapter is active, whatever is registered.
  • Spread. Requests go round-robin over all N adapters. At a concurrency of 64, up to min(N, 64) distinct adapters are in flight.

Same slots, same memory, same server start. Different number of adapters actually in the batch.

Predict first

At 64 registered slots, the concentrated regime serves about 3,127 output tokens per second. Where is the spread regime, relative to that?

Why a mixed batch costs more

A LoRA adapter adds two small matrices to each targeted projection. When a batch shares one adapter, every row is multiplied by the same pair: one pair of multiplications per projection over the whole batch, and the adapter's weights are read from GPU memory once per step.

When a batch spans 64 adapters, each row needs its own adapter's pair. The kernel splits the batch by adapter, reads 64 sets of weights per projection per step and runs 64 small multiplications instead of one larger one, at every layer of every decode step. That is the mechanism as the kernels are organised. The campaign measured the cost's size, not its breakdown inside the kernel.

Why the concentrated regime pays too

With the default specialize_active_lora = False, one dimension of the LoRA kernels' launch grid is max_loras + 1 whatever the batch holds. Slices for empty slots exit early but are still launched. At 64 slots a concentrated batch launches 65 slices per LoRA operation, against 2 at 1 slot. This is the registered-slot cost. It is not KV capacity, which never binds at this request shape (module 4).

What was not measured. A planned diagnostic would have split the registered-slot cost using --specialize-active-lora. At 64 slots it ran out of GPU memory during CUDA-graph capture at both budgets tried, so it was cut before the first measured run and its hypothesis (H4) withdrawn. The −450 tokens per second is reported unsplit.

Checkpoint

Say which line's slope is the registered-slot cost and which gap is the heterogeneity cost. Then say why max_loras being both the slot count and the in-batch cap forces the two regimes to separate the costs by traffic.

What a passing answer contains

The blue line's own slope is the registered-slot cost: more slots registered, the same single adapter doing the work. The red-to-blue gap at a given N is the heterogeneity cost: same slots, but N adapters active. Because one knob sets both the slot count and the in-batch cap, you cannot register 64 and cap the batch at 1 to isolate them. Traffic is the only lever left, so the experiment varies how many of the registered adapters the requests actually touch.

Follow-up to expect: "Which is bigger?" At 64 slots the heterogeneity cost is about 2.9 times the registered-slot cost (−1,290 against −450 tokens per second).

Module 3

Spread versus interval, then the knee

15 min

The bars

Open by testing what you already know. A 95% bootstrap interval of the median says where the median would land if the whole 24-start experiment were run again. It does not say where a single start lands. Individual starts scatter more widely than the bars, and a narrow bar says the median is pinned down, not that every start behaves alike.

This is also why the heterogeneity cost is paired within a start. Each start runs both regimes, in a random order, so the difference is taken inside one server start and start-to-start variation cancels out of it. The registered-slot cost compares concentrated at N with concentrated at 1 slot across starts, so it cannot cancel that variation, and its intervals are wider relative to its size.

The knee rule

The knee is defined on spread-regime throughput, with every registered adapter active. It is the fraction of throughput lost each time the adapter count doubles, against a threshold τ = 10% fixed before any measured run. The registered rule takes the first point estimate above τ.

Loss per doubling, with 95% intervals

The point estimate for 8 to 16 is 10.7%, which crosses 10%, so the registered rule puts the knee between 8 and 16. But the interval, 9.2% to 11.5%, straddles the threshold: the crossing is not resolved. The next two doublings are resolved, since their intervals clear 10% on the low side. If the 8-to-16 crossing were noise, the slot bound would be 16. The rule was registered to err toward fewer tenants, and here it does.

First, without the page: what do the bars in the main chart say, and what do they not say? Then: is the knee at 8 resolved, and what happens to the dollars if it is really 16?

What a passing answer contains

The bars say where the median would land on a re-run of the 24-start experiment. They do not say where one start lands, because starts scatter more than medians do. The knee at 8 is not resolved: the interval for the 8-to-16 loss is 9.2% to 11.5% and contains the 10% threshold. If it were 16, tenants would double and the cost per tenant would halve, from $101.24 to $50.62.

Follow-up to expect: "So why report 8?" The rule was registered before the data to take the first point estimate above τ, and to err toward fewer tenants. Reporting 16 after seeing the interval would be choosing the rule after the data.

Little's law and the three bounds

Little's law

In steady state, the number of requests in a system equals their arrival rate times the time each spends in it. That lets you recover a time you did not measure from two counts you did. Change any input below.

Defaults are the post's: 64 in flight at 8 slots, about 204 completions a second, 730-hour month, 9 requests of KV room at 8,192 tokens. One tenant's peak is 100,000 ÷ (730 × 3,600) × 3 ≈ 0.114 requests a second. The exact inputs give 251; the post rounds the per-tenant figure to 0.036 and gets 250.

The bound is an upper estimate for a reason the post states: the time in system was measured on 29-token requests. A request that really used 8,192 tokens would stay longer, and the bound would be lower. Even so, it sits far above the slot knee of 8, so slots bind first.

Why KV capacity cannot move latency here, and still matters

Each slot's weight buffers take GPU memory that would otherwise hold KV cache. Capacity falls from 78,208 tokens at 1 slot to 42,864 at 64, about 45% of the cache gone. But a request here holds 29 tokens, which vLLM stores in 16-token blocks, so each one takes two blocks, 32 tokens. Sixty-four in flight need 2,048 tokens. The scheduler never waits for KV, so the effect on TTFT or throughput at fixed concurrency is zero by construction. Memory matters as capacity: how many requests the GPU can hold, which becomes tenants.

Checkpoint

Reproduce 0.31 s, 0.036 requests in the system per tenant, and 250 from the numbers above. Then say why KV capacity cannot move TTFT at 29-token requests and still sets a tenant bound. Last: recompute how many requests the 42,864-token cache holds at 64 slots, counting in 16-token blocks, and check it against the 4.7%.

Worked answer

64 ÷ 204 = 0.314 s. One tenant's peak is 0.114 requests a second, so it keeps 0.114 × 0.314 ≈ 0.036 requests in the system. A cache with room for 9 requests at 8,192 tokens divided by 0.036 gives about 250 tenants. The cache holds 42,864 ÷ 32 = 1,339 requests, and 64 × 32 = 2,048 of 42,864 tokens is 4.8%, close to the logged 4.7%. Counting 29 tokens a request instead gives 4.3%, further from it.

KV cannot move TTFT because the cache never fills: the scheduler never waits for it. It sets a tenant bound because at long contexts a tenant's requests occupy cache for as long as they are in the system, so cache room divided by that occupancy caps how many tenants fit.

The post first printed 1,478 here, dividing by 29 and ignoring block rounding. It now says 1,339.

Module 5

The equivalence gate, and the amendments

25 min

Module 1 gave an argument that random adapters cost the same to serve as real ones. The pre-registration also required an empirical check before the campaign could start: 4 real public adapters against 4 synthetic ones in the same 8-slot server, each start running two spread phases over each set in a random order.

The rule

  • Statistic, per start: (synthetic − real) ÷ real, for TTFT p50 and for throughput.
  • Margin δ = τ ÷ 2 = ±5%. A synthetic bias smaller than that cannot move the knee by itself.
  • Pass if the 90% bootstrap interval of the median statistic lies inside ±5% for both metrics. That is two one-sided tests at the 5% level.
  • Resolution check, run alongside: the second real phase against the first, the same statistic. If it does not fit inside ±5%, the gate cannot resolve its own margin, and "no difference found" would mean nothing. The verdict is then inconclusive, not pass.
  • Fail otherwise: the resolution check fits, but the statistic is not inside.

The order matters. The code asks first whether both metrics are resolved. Only then does it ask whether both are inside.

Apply the rule to each stage

How it got to 137, in order

  1. The pilot, 24 starts, was inconclusive. One compiled cold and was excluded, leaving 23. Single-phase TTFT varied by roughly ±10 to 15% between phases of one start, and 23 starts could not resolve ±5% through that.
  2. Amendment 1, written after that verdict and in response to it, enlarged the gate to 144 starts in a fresh store, with nothing else changed. The pilot is kept and not pooled.
  3. The larger gate lost 52 starts to a host fault. Run indices 92 to 143 all landed on one pod whose driver (570.195.03) could not run the image: CUDA Error 804, dead before serving a request. An endpoint restriction to CUDA 13.0 hosts did not prevent the placement, and the cause is not known. Of the 92 that ran, 4 compiled cold and were excluded.
  4. The 88 usable starts were inconclusive. TTFT was inside the margin, but its resolution check just missed.
  5. Amendment 3 extended the gate by exactly 52 replacements, decided after seeing the 88-start verdict. Three replacements hit the same CUDA error on a host with the same driver, and a stop-on-repeated-failure guard halted the run. Those three were counted and not replaced again.
  6. Final: 196 scheduled, 55 failed, 4 excluded as cold compiles, 137 usable. Verdict: pass.

Two things the order does and does not buy

Amendment 3 is a data-dependent extension: the decision to run more followed a verdict the author had seen. The defence is that the 52 lost starts were a host fault that never ran a phase, so the extension restores a sample size Amendment 1 had fixed in advance rather than choosing a new one. A reader should still discount it, because the interim result was known when the extension was chosen. What makes it checkable is that the amendments were appended without editing anything above them, so git history shows the order.

The gate covered one point: 8 slots, 4 adapters of each kind. That synthetic adapters stand in for real ones at the other points rests on module 1's argument, not on a measurement at each point. The TTFT resolution check passes by 0.05 points, and its interval sits above zero: the second phase over the same real adapters ran about 2% slower. That is an order effect that was not investigated.

Checkpoint

State the rule, including why it has three verdicts. Then, from the 88-start result, give the verdict and say why. Last: what separates Amendment 3 from a forking path, what should the reader still discount, and why does the stop-on-repeated-failure guard exist?

What a passing answer contains

Three verdicts because "no difference found" only means something if the gate could have found a difference of the size that matters. Pass needs both metrics resolved and inside ±5%. Inconclusive means the gate could not resolve ±5% at all. Fail means it could, and the synthetic set was outside.

88 starts: TTFT statistic −1.16% [−2.54%, +0.75%] is inside, but its resolution check +2.24% [−0.11%, +5.81%] is not, since 5.81% is past 5%. So inconclusive, even though throughput was resolved and inside.

Amendment 3 restores a fixed sample size after a fault that never ran a phase, with the order in git. Still discount that the interim verdict was known. The guard exists because the runner had no stop on repeated failures: it kept submitting onto a bad host, which is how 52 starts were lost and, later, 3 more.

The simulator failed its own test

Artifact 4 pre-registered a test its simulator had to pass before it was trusted: reproduce a real one-GPU, three-model replay at its bursty regime with Zipf skew 1.0. That is the reference point used here. The outcome was failed: 10 of 13 judged bins fell outside the band of three real repeats (3 agreed), the largest miss was 67.8 s, and 1 of 2 held-out interference cells passed. The swap count agreed, 11 predicted and 10 real in all three repeats. Nothing in artifact 4's cost file is validated, at this point or any other.

Which way does the swapped bar err?

The comparison is not like for like

Artifact 4's costs come from a simulated fleet of 20 Qwen3-1.7B models with 256-token outputs under its own traffic model. This artifact's come from Qwen3-4B with 16-token outputs at a fixed concurrency of 64. Artifact 4 moved to Qwen3-1.7B because its primary pair, Qwen3-4B and Qwen3-4B-Base as two co-resident engines, failed its own memory go/no-go (KV capacities of 9,456 and 9,520 tokens against 16,384 required). The three bars share a unit and a GPU rate and nothing else that was measured.

What the comparison can carry is the shape of the choice. Swapping pays per switch, in the time it takes to bring a model onto the GPU. Resident adapters never switch, and pay per co-active adapter, in throughput. A like-for-like number needs artifact 4's swap measured on Qwen3-4B, or this sweep run on Qwen3-1.7B. Neither was run.

Limits the post states about itself

  • One base model, one GPU, one rank, one request shape (13 prompt and 16 output tokens at concurrency 64). The knee at another rank, model or prompt length is unmeasured.
  • vLLM 0.27.1, pinned by image digest, in a fast-moving area. Claims are dated 2026-10.
  • The all-resident case only. Swapping adapters from CPU memory is a sequel.
  • The registered-slot cost is unsplit; the diagnostic was cut.
  • The regime check is a sample: a once-a-second gauge, not a count per batch.
  • All 191 successful campaign starts ran on one host. Host-to-host variation is not in the intervals.
  • The rate, $1.1095 per GPU-hour, is an estimate from one billing sample.
  • The gate was extended after its result was seen, and the knee's first crossing is not resolved.
Checkpoint

Against what was validated: which of the three bars rest on a failed simulator, which way each is known to err, why the model sizes differ, and why the adapter bar is an upper bound. Then name three limits the post states about itself.

What a passing answer contains

Dedicated and swapped come from the failed simulator; the adapter bar is this artifact's own measurement but is a bound, and inherits the swapped bar's caveat when compared. The swapped bar has no known direction of error: at the 37.8 s swap time the simulator predicted latency higher than real in every missed bin, and at about 25 s it predicted lower in every bin that still missed. The dedicated bar was not tested by the gate. The sizes differ because artifact 4's Qwen3-4B pair failed its memory go/no-go. The adapter bar is an upper bound because 8 tenants is a lower bound, since adapters could also be swapped from CPU memory.

Follow-up to expect: "So can you say adapters beat swapping?" Artifact 4 says the ordering is wide, but it did not test whether the model's error is small enough to leave the ordering unchanged, so the comparison is only as firm as the swapped bar.
