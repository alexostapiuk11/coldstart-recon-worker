Which tool-calling failures tool presentation moves

Read first: How these experiments earn trust

No data yet: no campaign has run, and no result is shown. This page shows the question, the instrument, the predictions and the controls only. Hold one model fixed and change only how its tools are presented: 2 to 4 tools or 20 with look-alikes, terse or rich descriptions, loose or strict schemas. Which kind of failure moves: a call that is not valid, a call nobody asked for, a missing call, the wrong tool, or the wrong arguments? And what does each presentation cost per successful call? 49 candidate scenarios in seven public or synthetic domains, graded by rule with no LLM judge. The sources disagree in one place (see the known contradiction); this page follows the amendment that governs.

Answer first

I'm testing whether the way you present tools to an LLM changes which failures you get, holding the model fixed: two to four tools or twenty with look-alikes, terse or rich descriptions, loose or strict schemas. A rule-based grader, not an LLM judge, puts every response into one of six categories, and the intervals resample scenarios rather than calls, because a scenario that confuses the model does so on every rerun. The harness, a 49-scenario suite and the grader's tests are built and merged; the predictions are in an approved design but not yet frozen in a pre-registration, and no campaign has run, so I can give you the design and the bets, not results.

Need to know first

C1Six categories, and the first rule that applies wins

The model executes nothing: it emits a structured request (a tool, JSON arguments) and the harness decides what to do with it, so every failure is a property of that request and needs no judgment about meaning. Provider errors, refusals and truncations are excluded first and counted per cell. Then: MALFORMED (not a valid call to a tool that was shown: unparseable, a tool not in context, a required key missing, a wrong JSON type), SPURIOUS (a call where none was expected), MISSING (no call where one was), WRONG_TOOL, WRONG_PARAMS (a wrong value, enum or pattern miss, or an unknown key), CORRECT. The category depends on what was rendered: a call to get_current_weather is MALFORMED in a cell that shows two other tools and WRONG_TOOL in the 20-tool cell that shows it.
Like
The model is a client sending an RPC, the harness a gateway validating it: parse, then schema, then routing, then business rules. The order is part of the contract, as a 400 is decided before a 404.
Used by: D3 Grade by rule, against one canonical schema

C2The eight cells

Count: the scenario's own 2 to 4 tools, or exactly 20 (those, 4 to 6 look-alikes written for the scenario, and filler from its own domain first, then others). Richness: terse one-liners or rich descriptions. Strictness: loose types (only the first required parameter in required) or strict enums, patterns and every required key. Baseline: low, terse, loose. Rich text may state a constraint in words that a strict schema states in structure, so richness and strictness overlap.
Like
A configuration matrix in which each axis changes one thing and the system prompt is one fixed text in every cell, like a deploy matrix that differs only in the flag under test.
Used by: D1 Vary the presentation, hold the model fixed, cross the factors · D2 Strictness is schema content; constrained decoding stays off

C3Strictness is schema content, and every call is graded against one canonical schema

Each tool has one canonical schema, its strict form, and every call in every cell is graded against it, whatever the model was shown. A loose schema is charged for constraints it never showed: that is the measurement of what loose costs, not a bug. Provider strict mode (constrained decoding) is off in all eight cells, because it would make MALFORMED nearly impossible by construction and test the API, not the model; one exploratory slice turns it on.
Like
Contract testing: a consumer's request is validated against the provider's real contract, not the subset the docs showed. And a type system that makes invalid states unrepresentable versus documentation plus a validator at the edge: this study asks whether the model reads the documentation.
Used by: D2 Strictness is schema content; constrained decoding stays off · D3 Grade by rule, against one canonical schema

C4The unit of independent variation is the scenario

N reruns of one scenario carry between one and N scenarios' worth of information, set by the intra-scenario correlation ρ. S scenarios × N repetitions have effective size S·N / (1 + (N − 1)ρ), which approaches S/ρ however many repetitions are added. Intervals resample whole scenarios; Wilson intervals are used only within one scenario.
Like
A flaky test failing 20 times in CI is one bug with 20 symptoms. A dashboard counting failures counts symptoms; the bootstrap over scenarios counts bugs.
Used by: D4 The scenario is the unit; scenarios and repetitions are sized together

C5Main effects, interactions and the scale

A main effect is the high-level rate minus the low-level rate, averaged over the other two factors, in percentage points. An interaction is one factor's effect at the other's high level minus its effect at the low level: the difference, as the code computes it, not that difference halved. Say which convention you mean. The scale is fixed in advance because an interaction on the percentage-point scale can vanish on a ratio scale.
Like
An ablation table where you ask not only whether a component helps, but whether it helps more on a large cluster than on a small one.
Used by: D1 Vary the presentation, hold the model fixed, cross the factors

C6The baseline band, and what it selects

Every candidate runs 10 times at the baseline cell and is included if its correct rate falls in a band, proposed as 0.10 to 0.90 and frozen at step 1. It picks where the instrument has resolution: scenarios a model always passes could hide a real effect. Every candidate and decision is published, and excluded ones stay in the repository. One reading the sources do not state: a rate strictly between 0 and 1 means the reruns disagreed, so the band also selects for flipping; how many candidates survive is what the pilot measures.
Like
Sizing a load test: choose a load at which the system sometimes fails, because a load at which nothing ever fails cannot show which change helps.
Used by: D6 Pre-register in two dated steps, behind a spend guard

C7Recovery, and the identical retry

A mock service rejects a call as the scenario says (an invalid parameter, a contradicting result, a timeout or a malformed payload) in one of two formats: actionable (names the parameter, says what to do) or opaque (Error: invalid request.). Up to three attempts follow. Identical retry: the first action after the error repeats the failing call unchanged. For a rejection that is a loop; for a timeout it is the right move, so H4 counts the persistent kinds only. A conversation ends as recovered, gave_up (stopped calling, no success claim; includes asking the user), hallucinated_success (stopped calling, a success-shaped message with no disclosed failure: a pattern proxy with known misses), or budget_exhausted (rejected at the third attempt, neither of the other two).
Like
HTTP semantics: a 400 with a field error must not be retried unchanged, a 504 may be if the call is idempotent. An agent retrying a non-idempotent call after a timeout meets the duplicate-payment problem of artifact 6.
Used by: D5 Keep the recovery sub-design, with a floor rule and at least 20 scenarios

C8Cost per successful call, and the retry walk

All spend, failed attempts included, divided by correct calls. A retry policy of up to three attempts is costed by walking each scenario's recorded reruns in order, not with c / (1 − f), which assumes each retry is an independent draw. If a failing scenario fails again, the formula understates the cost: in a worked example with f = 0.3 and a cap of 3, the formula and independent failures give 1.43 calls per success, and 2.29 if the failing 30% of scenarios always fail.
Like
Capacity planning for retries: independent failures make retries cheap, but a poison message that fails every time makes every retry pure cost.
Used by: D4 The scenario is the unit; scenarios and repetitions are sized together

C9Known contradiction in the sources: the August learning guide against the amendment

The August design's learning guide (§9b) and its definition of done (§10) predate the amendment that governs the design. Module 4 teaches "20 scenarios × 20 repetitions = 400 observations"; the amendment sets at least 24 scenarios and N from the pilot's ρ. Module 5 and §10 present Wilson intervals for reported proportions; the amendment allows Wilson only within one scenario. Module 6 teaches temperature-0 nondeterminism as the headline (August H5); the amendment withdraws it and cites near-deterministic reruns. The amendment says it governs, and its supersession list (§11) replaces §5's Wilson-on-cell-rates and the ~20-scenario count, but does not name §9b's modules 4 and 5 or §10's Wilson item. This page follows the amendment.
Like
A runbook that predates an incident-driven change to the design: where the two disagree, the later, approved document is the one to follow, and the stale one is a known trap.
Used by: D4 The scenario is the unit; scenarios and repetitions are sized together

Requirements that drove everything

R1One model, eight renderings

Every scenario is rendered in all eight cells (tool count × description richness × schema strictness), and the renderings differ only in the factor being manipulated.
Otherwise a difference cannot be pinned on presentation. It is the same single-variable discipline the other artifacts apply to their arms.
Answered by: D1 Vary the presentation, hold the model fixed, cross the factors · D2 Strictness is schema content; constrained decoding stays off

R2Grade by rule, against one contract

Every response is graded by an ordered procedure into exactly one of six categories, against each tool's single canonical schema, with a versioned normalizer. No LLM judge.
A judge adds its own variance to the quantity under study, and a harness that answers differently twice cannot be adopted. Each category points at a different fix.
Answered by: D3 Grade by rule, against one canonical schema

R3The scenario is the unit

Rates are averaged per scenario, intervals resample whole scenarios, and the number of repetitions is sized from the pilot's intra-scenario correlation.
Reruns of a scenario the model finds confusing fail for the same reason each time. Treating calls as independent makes intervals far too narrow and manufactures significance.
Answered by: D4 The scenario is the unit; scenarios and repetitions are sized together

R4Recovery: does the model loop?

After an injected tool error, measure whether the model repeats the failing call unchanged, with the error message either actionable or opaque.
Repeating a failing call verbatim turns one error into a token-burning loop; an actionable message should prevent it. It is a mechanism-level prediction that gets tested, not asserted.
Answered by: D5 Keep the recovery sub-design, with a floor rule and at least 20 scenarios

R5Rules and spend fixed before data

Hypotheses, band, grading and floors are committed before the pilot; the scenario count, repetitions, included scenarios and approved spend before any campaign call. No paid call runs without a stated call count and cost.
N depends on what the pilot measures, git timestamps must show the order, and the portfolio's spend rule is made mechanical by a guard.
Answered by: D6 Pre-register in two dated steps, behind a spend guard

R6Public or synthetic only

Every scenario, tool and schema is public (a BFCL seed) or authored in neutral domains; nothing derives from the author's employer. A scan of the data files fails the tests unless the author has signed off each hit.
The author's confidentiality boundary. The scan cannot read intent, so a pre-publish check by the author remains.
Answered by: no decision. A constraint on every decision, enforced by a data-file scan and the author's sign-offs (amendment §6), not the outcome of a choice among options.

Core decisions

D1Vary the presentation, hold the model fixed, cross the factors

Serves: R1 One model, eight renderings
Seen in: F3 Hypotheses H1 to H5 as the approved amendment words them (not yet frozen; results pending)
Problem
Benchmarks vary the model and hold the prompt fixed. The question an engineer faces every time a tool is added is how to present the tools. The plausible finding is an interaction: rich descriptions matter little with three tools and a great deal with twenty look-alikes.
Options
Rank models on tool calling, as the leaderboards doChange one factor at a timeA 2×2×2 factorial over tool count, description richness and schema strictness, one model carrying it
Because
One factor at a time would miss the interaction; holding the model fixed answers a decision made on every new tool.
Cost
Eight cells per scenario; H1 replicates Guo et al.; the novelty claim is only as wide as a moderate-confidence search.
Full reasoning and cost
Because
Changing one factor at a time reports two bland main effects and misses the interaction, which is the plausible finding. Holding the model fixed answers a decision made on every new tool, not once. The amendment also found single factors already studied, and no published work that crosses the factors, uses plausible look-alikes or breaks effects down by failure category (moderate confidence).
Cost
Eight cells per scenario, and a second and third model only on the best and worst cells. H1 is a replication of Guo et al. under a stricter design, not a first. The novelty claim reaches only as far as that search did.

D2Strictness is schema content; constrained decoding stays off

Serves: R1 One model, eight renderings
Problem
Read literally, the August strict arm would let a provider's strict mode do the work, making the malformed category nearly impossible by construction. That would test the API, not the model.
Options
The strict arm is the provider's strict mode, as the August design read itThe strict arm is the schema the model sees, with decoding unconstrained in all eight cellsSchema content in all eight cells, plus one exploratory slice with strict mode on
Because
The question is whether the model reads the schema, not whether the decoder enforces it; one exploratory slice turns strict mode on.
Cost
The exploratory slice's schemas differ (null unions); the vendors' guarantees are the amendment's reading of their docs.
Full reasoning and cost
Because
The question is whether the model reads the schema, not whether the decoder enforces it. High strictness renders enums, patterns and a full required list; low strictness renders loose types. The slice answers the practitioner's question, "if I turn strict mode on, which failures are left?", and is labelled exploratory in those words.
Cost
The slice's schemas differ from the factorial's: OpenAI's strict mode rewrites optional parameters into unions with null. The provider guarantees come from documentation the amendment read, not re-checked here. "Strict" in this study never means a vendor flag.

D3Grade by rule, against one canonical schema

Serves: R2 Grade by rule, against one contract
Seen in: F1 What the suite is made of (an instrument fact, not a result) · F2 The grader on hand-labelled boundary cases (a control, not a result)
Problem
A grader needs a fixed standard. An LLM judge superimposes its own variance on the model's, and grading against whatever schema was rendered would let the instrument create the failures it measures.
Options
An LLM judgeOrdered rules, checking conformance against the schema the model was shownOrdered rules, checking every call against one canonical strict schema per tool
Because
A judge adds variance, and grading against the rendered schema would make strictness appear to cause the failures it constrains.
Cost
Only enumerable, structurally checkable calls; a loose cell can be marked wrong for an unseen constraint, by design.
Full reasoning and cost
Because
A judge's variance would contaminate the quantity under study, and a harness that answers differently twice is not something anyone builds on. Grading against the rendered schema would give the strict arm more ways to be MALFORMED, so strictness would look like it causes the failures it constrains. Structure is checked first, then value, so one wrong value is scored alike in every cell.
Cost
Only scenarios whose correct calls can be listed in advance qualify, so it measures structurally checkable calls, a subset of agent correctness. A loose cell can be marked wrong for a constraint it never showed, by design. The normalizer silently sets results, so its rules are versioned and a change is breaking. A "check first" call is graded WRONG_TOOL, because grading is single-turn.

D4The scenario is the unit; scenarios and repetitions are sized together

Serves: R3 The scenario is the unit
Seen in: F4 Same 80 failures in 400 calls, two splits across scenarios (constructed, not data)
Problem
Reruns of a scenario are correlated, so the count of calls overstates the information. The August design had scenarios shrink before repetitions and used Wilson intervals on proportions, both resting on rerun variance being the headline.
Options
About 20 scenarios with many repetitions, scenarios shrinking first, Wilson intervals on cell proportions (August)N from the pilot's ρ at 95% of the S/ρ limit with a floor of 5, at least 24 scenarios, a bootstrap over scenarios, Wilson only within one scenario (amendment)
Because
With near-deterministic reruns the information is in the scenarios, and Wilson over all calls treats them as independent.
Cost
Authoring time limits S; the band caps ρ near 0.61 so N is 13 or more; the near-deterministic premise is a cited abstract.
Full reasoning and cost
Because
With near-deterministic reruns an extra repetition adds almost nothing to a cell rate's interval; the information is in the scenarios. A Wilson interval over all S·N calls treats them as independent, the error the clustering exists to prevent. If the budget binds, N drops to its floor before S drops.
Cost
Authoring time, not money, limits S. With 10 pilot repetitions and the band, the realised ρ is at most about 0.61, so N is at least 13. The premise (near-deterministic reruns) is the Noise Floor Audit's, read by the amendment on abstracts and not checked here.

D5Keep the recovery sub-design, with a floor rule and at least 20 scenarios

Serves: R4 Recovery: does the model loop?
Seen in: F1 What the suite is made of (an instrument fact, not a result) · F3 Hypotheses H1 to H5 as the approved amendment words them (not yet frozen; results pending)
Problem
Whether an actionable error stops the model repeating a failing call is a clean mechanism-level prediction. But prior work reports that identical repeats are rare, so H4 may have nothing to measure, and the bootstrap needs enough scenarios to give a verdict.
Options
H4 unconditional, as the August design had itH4 with a pre-registered floor: if the opaque arm's identical-retry rate is under 5%, report it as not testableEight recovery scenarios, the amendment's first plan
Because
The floor keeps a floor effect from reading as evidence, and fewer than 20 scenarios could never give a bootstrap verdict.
Cost
Recovery's estimate rose to at most about $14; H4 may be not testable; hallucinated_success is a regex proxy with known misses.
Full reasoning and cost
Because
The floor keeps a floor effect from reading as support or as refutation; Gumaan and Kraishan are the reason it exists. Eight scenarios could never yield a verdict, because the harness refuses a bootstrap over fewer than 20. Recovery scenarios are call scenarios with a recovery block added, so the extra authoring is small.
Cost
The estimate for recovery rose from about $5.43 to at most about $14. H4 may end as not testable. hallucinated_success is a regex proxy with known misses. A wrong first call can never recover under a transient error, so recovery is also reported given a correct first call.

D6Pre-register in two dated steps, behind a spend guard

Serves: R5 Rules and spend fixed before data
Seen in: F3 Hypotheses H1 to H5 as the approved amendment words them (not yet frozen; results pending)
Problem
N depends on what the pilot measures, so not everything can be committed before the pilot. But every rule that does not depend on the pilot should be written down before it, and a paid run needs a hard rule.
Options
One step: everything committed before the pilot, as the August design saidTwo dated steps: rules before the pilot; the scenario count, repetitions, included list and approved spend after it and before any campaign call
Because
N depends on the pilot, so rules go in before it and S, N and spend after it; a ledger guard makes the spend rule mechanical.
Cost
Step 1 is not yet committed, so H1 to H5 are not frozen; plan 1's review changed four statistical details before registration.
Full reasoning and cost
Because
The pilot is itself a paid run and N depends on it; artifact 4 did the same. Post-hoc changes are numbered, dated amendments, never edits. The values are to be held as code, with a test that fails if the document and the code disagree (the record exists; the values file comes with step 1). The spend guard refuses to start without an approved amount that covers the estimate plus headroom, and reserves each call's worst case in a ledger before the call.
Cost
Step 1 is not yet committed: until it is, the hypotheses exist only in the approved amendment and are not frozen. Plan 1's review changed four statistical details before any registration was committed (amendment §14 items 8 to 11). The guard's per-call bound is conservative, so metered spend over-counts failures; billed against metered spend is reconciled before publication.

Interview card

30 seconds. I'm testing whether the way you present tools to an LLM changes which failures you get, holding the model fixed: two to four tools or twenty with look-alikes, terse or rich descriptions, loose or strict schemas. A rule-based grader, not an LLM judge, puts every response into one of six categories, and the intervals resample scenarios rather than calls, because a scenario that confuses the model does so on every rerun. The harness, a 49-scenario suite and the grader's tests are built and merged; the predictions are in an approved design but not yet frozen in a pre-registration, and no campaign has run, so I can give you the design and the bets, not results.
The 2-minute version

Tool-calling benchmarks rank models with the prompt held fixed. I asked the question an engineer faces every time they add a tool: holding the model fixed, does how I present my tools change which failures I get? Each scenario is a plain data file: a user message, the two to four tools it needs, four to six look-alike tools written for it, and the exact calls that count as correct. A renderer produces eight versions: few tools or twenty, terse or rich descriptions, loose or strict schemas. It is a factorial because the plausible finding is an interaction: rich descriptions should matter more with twenty look-alikes than with three tools. The grader puts each response into one of six categories by ordered rules, always against one canonical strict schema, so a loose schema's cost shows up instead of being forgiven. Provider strict mode stays off in all eight cells, because constrained decoding would make malformed calls nearly impossible by construction and I would be testing the decoder. The statistics follow from one idea: reruns of a confusing scenario are correlated, so I average per scenario, bootstrap over scenarios, and size the repetitions from the pilot's correlation. I also convert everything to cost per successful call, walking the recorded reruns rather than using the textbook retry formula. What exists is the offline core, a 49-scenario suite, and tests against a stub; what does not is any model result. The five hypotheses are worded in an approved design and get frozen in a committed pre-registration before the pilot runs.

Hard follow-ups

Tool-calling benchmarks already exist. What is new here?

They vary the model and hold the prompt fixed; this holds the model fixed and varies the presentation. The literature has since covered single factors and rerun noise: the amendment names Guo et al. as the closest work to H1, so H1 is framed as a replication under a stricter design, and the Noise Floor Audit as the closest to H5, pointing the other way. What the search found no one publishing, at moderate confidence, is a balanced factorial with plausible look-alikes, broken down by failure category and converted to cost per successful call. I claim that only as far as that search went, and none of it has produced a result yet.

400 calls in a cell: why is the interval not based on 400?

Reruns of one scenario are correlated, so the effective size is S·N / (1 + (N − 1)ρ), between S and S·N. Take two constructed datasets with the same 80 failures in 400 calls. If the failures are spread over the scenarios the interval is near ±4 points; if four scenarios fail every time and sixteen never do, resampling scenarios gives 5 to 40, while a Wilson interval on 400 calls gives the same narrow answer for both. So I resample whole scenarios and use Wilson only within one scenario.

You grade a loose-schema call against a schema the model never saw. Isn't that unfair?

It is the measurement: what a loose schema costs is exactly the constraints the model was not told. Grading against the rendered schema would give the strict arm more ways to fail, so strictness would look like it causes the failures it constrains, a confound the instrument would create. The README says so, and rich descriptions can state a constraint in words, which is part of the richness-by-strictness interaction.

Provider strict mode is on and the malformed rate is zero. What have you learned about the model?

Almost nothing about its structural ability, because constrained decoding guarantees a conforming call except on a refusal, a truncation or enum capitalisation (the vendors' claim as the amendment read it, not re-checked here). What remains informative is the wrong tool, value-level wrong parameters, missing calls and spurious calls. That is why strict mode is off in the eight cells and run as one labelled exploratory slice.

The amendment expects near-deterministic reruns, yet your band wants scenarios with a 10 to 90% baseline pass rate. How can both hold?

The sources do not resolve it; this is a reading, not a finding. A rate strictly between 0 and 1 over 10 reruns means those reruns disagreed, so the band selects for flipping. The amendment lists few survivors as a risk and answers it by authoring more candidates before step 2, and does not widen the band after the pilot. If reruns barely flip, authoring more may not help, and I would say so. The pilot's survival rate is the measurement, so this is pending. The deviations log notes one consequence already: the band caps the realised ρ near 0.61, so N is at least 13.

Why not cost a retry policy as c / (1 − f)?

That formula assumes each retry is an independent draw. With near-deterministic reruns a scenario that fails tends to fail again, so it understates what retries cost; in a worked example with f = 0.3 and a cap of 3, 1.43 calls per success becomes 2.29 if the failing 30% of scenarios always fail. The study walks each scenario's recorded reruns in order. It is the scenario-as-unit argument expressed in money.

Limits: do not claim more. No results exist: no hypothesis has an outcome and no cost per successful call has been measured. The hypotheses are worded in the approved amendment and are frozen only when pre-registration step 1 is committed; it has not been, and no pilot or campaign records are committed. When results exist they will hold for the pinned model snapshots on their run dates, each at the provider's most deterministic available setting (which may be the provider default, recorded as a deviation), for structurally checkable single-call scenarios in seven public or synthetic domains, one call per turn, and a suite chosen by a baseline band. A "check first" call is graded WRONG_TOOL because grading is single-turn; hallucinated_success is a regex proxy with known misses; the high-count filler is partly cross-domain. The prior-work table is cited from abstracts the amendment's author read and is not re-read here. The sources contradict each other in one place (the August learning guide against the amendment) and this page follows the amendment. A later revision of the pilot plan is uncommitted and is not used here.

Recall check

Answer out loud first, then open.

A model emits get_current_weather in a cell that shows only get_forecast and get_air_quality. Which category? And if the cell shows 20 tools including it?

MALFORMED: a tool that was not shown is structural. In the 20-tool cell the same call is WRONG_TOOL (a confusable). The category depends on what was rendered, by design.

The user only says thanks, so no call is expected, and the model calls a shown tool with a required argument missing. Category?

MALFORMED. Structure is checked before SPURIOUS, so the ordered rules decide it, not the intent.

Why is a loose-cell call graded against the strict schema?

That is the measurement of what a loose schema costs. Grading against the rendered schema would give the strict arm more ways to fail and make strictness look harmful, a confound the instrument would create.

Which three outcomes are excluded before any rate is computed?

API_ERROR, REFUSED and TRUNCATED. Each is counted per cell, and a cell where they together exceed 2% of its calls is flagged.

Why is provider strict mode off in all eight cells?

It would make MALFORMED nearly impossible by construction and test the decoder, not the model. One labelled exploratory slice turns it on.

What is the effective sample size, and what does it approach?

S·N / (1 + (N − 1)ρ), approaching S/ρ as N grows. At high ρ another repetition buys almost nothing, so the information is in the scenarios.

At ρ = 0.9 and 30 scenarios, what does going from 5 to 40 repetitions buy?

Almost nothing: effective size rises from 32.6 to 33.2 (the amendment's example). Spend on scenarios, not reruns. The band caps the pilot's ρ near 0.61, so the rule for N lands at 13 or more.

Where are Wilson intervals used in this design?

Only within one scenario, where the repetitions are the unit. Cell rates and effects use a bootstrap that resamples whole scenarios.

How is an interaction computed here, and what should you say about the convention?

One factor's effect at the other's high level minus its effect at the low level, on the percentage-point scale. Say that it is the difference and not halved, and that the scale was fixed before the data.

Why does H4 count only the persistent error kinds?

After a rejection an identical retry is a loop, but after a timeout it is the right move if the call is idempotent. Counting both would blur the pathology H4 tests.

What is H4's floor rule?

If the opaque arm's identical-retry rate has a point estimate under 5%, H4 is reported as not testable at this rate. It counts neither as support nor as refutation, and Holm runs over the other four.

A conversation ends with the model stopping and saying it could not retrieve the forecast. How is it recorded?

As gave_up, not hallucinated_success: the text discloses a failure. A success-shaped message that discloses nothing would be the hallucinated kind, by a regex proxy with known misses.

Which sources contradict each other here, and which do you follow?

The August design's learning guide (modules 4 to 6) and definition of done teach 20 × 20 observations, Wilson intervals for proportions and temperature-0 variance as the headline. The 2026-10-08 amendment governs where they conflict, so scenarios and N are sized together, Wilson is within one scenario, and that H5 is withdrawn.
