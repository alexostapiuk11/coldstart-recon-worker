Where a vLLM cold start goes

WhyConceptsViewsDecisionsFlowResultsInterviewRecallSources

Why it exists

When a vLLM server starts cold on a rented GPU, where does the time go? And which of its two empty caches is worth warming more: the model weights, or the engine's compiled code?

Requirements that drove everything

Split one cold start into named phases, and label what cannot be attributed instead of hiding it.
The two caches act on different phases: weights on loading, compile on engine start. One "startup" bar would hide half the experiment. And many published cold-start numbers quietly give all the time to stages the author could see; a named bucket for "time I cannot attribute, and why" is more credible.
Change exactly one thing between the set-ups being compared.
Otherwise a difference cannot be pinned on a cache. Same image, entrypoint and engine flags for every arm; only the cache configuration differs.
Report the distribution and its uncertainty, not an average.
Cold starts are skewed with a heavy tail, so a mean describes no real run. A claim like "cache X matters more" needs its own interval, not two point estimates side by side.
Fix the hypotheses, exclusion rules, stopping rule and headline rule before the first paid measurement run.
The git timestamps then show the rules came before the data, later amendments are dated and labelled, and the headline cannot be picked by which result cost the most effort.
Run only proven code on paid GPUs, and let anyone re-derive every number on a laptop.
The whole budget was $200, and debugging on live GPUs is what eats it. A number a reader cannot re-derive from the committed data is one they have to take on trust.

Need to know first

Arms A, B and C

Three cache set-ups. A: weights downloaded from the model hub, compile cache cold. B: weights read from a network volume, compile cache cold. C: weights from the volume, compile cache warm. A to B buys the weight cache; B to C buys the compile cache. For what weights, the compile step and a serverless cold start are, see P1, LLM serving on a GPU.

Contrast, and difference of contrasts

A contrast is the difference between two arms' medians: A minus B is what the weight cache saves, B minus C is what the compile cache saves. The difference of contrasts is (A minus B) minus (B minus C). Negative means the compile cache saved more. It gets its own bootstrap interval, because a ranking is only a finding if that interval excludes zero.

Pre-registration

Writing the hypotheses, analysis plan, exclusion rules, stopping rule and headline rule into a committed file before the first paid measurement run, so the git history shows they came first. Here: docs/experiment.md, committed four days before the first run.

System views (C4)

Who and what the study touches

The study rents GPUs from RunPod serverless, one job at a time. Weights come either from the model hub (arm A) or from a network volume RunPod mounts into the worker (arms B and C). The output is a post plus the raw data, for engineers and managers on inference-platform teams.

  • Author — designs, runs and publishes
  • Cold-start study — 300 measured cold starts, 3 cache set-ups
  • Reader — inference-platform engineers and managers
  • Network volume — staged weights and warm compile cache
  • RunPod serverless — one RTX 4090 job at a time, EU-RO-1
  • Model hub — Qwen3-8B at a pinned revision

  2. Cold-start study → Reader: post + raw data
  3. Cold-start study → RunPod serverless: rents GPU jobs
  4. RunPod serverless → Network volume: arms B, C read
  5. RunPod serverless → Model hub: arm A downloads

The runnable parts

The laptop side schedules, submits and stores; the worker image runs vLLM on the rented GPU and sends its measurements back as the job result. Analysis never touches the platform: it reads the stored lines on a laptop.

  • Driver + scheduler — laptop: seeded triples, submit, clock A
  • RunPod endpoint — queues the job, boots a worker, clock C
  • JSONL store — append-only, one line per run
  • Worker image — handler + probe running vllm serve, clock B
  • Model hub — weights for arm A
  • Analysis + figures — laptop only: partition, bootstrap, charts
  • Network volume — weights for B and C, compile cache for C
  1. Driver + scheduler → RunPod endpoint: job in, result out
  2. RunPod endpoint → Worker image: starts container
  3. Worker image → Model hub: arm A download
  4. Worker image → Network volume: arms B, C
  5. Driver + scheduler → JSONL store: appends a record
  6. JSONL store → Analysis + figures: reads rows

Inside one run: where the phases come from

The log parser and the run record live on the laptop; everything else runs inside the worker. The stage recorder stamps phase boundaries on one monotonic clock, and the raw vLLM log goes back with the result. On the laptop the driver parses the log into engine sub-phases and builds the record. Sub-phases the log does not delineate are stored as merged, not guessed.

  • Handler — reads arm and run id from the job
  • Cache config — arm to two paths: weights, compile cache
  • Cache-dir checks — empty cold dirs, refuse missing volume, snapshot
  • Result bundle — marks, log lines, warmup, cache state
  • Stage recorder — monotonic marks, clock B
  • Probe — starts vllm serve, sends ten requests
  • Log parser (laptop) — log lines to compile, profiling, capture
  • Run record — one self-describing JSON line
  • vLLM server process — prints its own startup phases
  1. Handler → Cache config: arm, run id
  2. Cache config → Cache-dir checks: paths
  3. Cache-dir checks → Probe: then start
  4. Probe → vLLM server process: reads stdout
  5. Probe → Stage recorder: marks S1 to S7
  6. Stage recorder → Result bundle: clock B marks

One run, in order

Follow the step numbers. Clock A (laptop) brackets the whole job; clock B (worker) starts when the probe starts. Platform time is total minus clock B time, so besides the queue it holds handler set-up, teardown and the driver's 5 s polling. A failed run is still stored as a row and never retried.

Core decisions

Three arms, one variable

ProblemA cold vLLM replica starts with two empty caches: the weights and the engine's compiled code. To say which matters more, each comparison must change one thing only.
OptionsTwo arms, hub weights vs volume weights (the fallback if this vLLM did not compile at startup)Add a baked-image arm, with the weights inside the container imageAdd the fourth cell: weights cold, compile cache warmOne variable, cache configuration, at three levels: A, B, C
ChoseOne variable, cache configuration, at three levels: A, B, C
BecauseA to B isolates the weight cache. B to C isolates the compile cache with weight handling held constant. The configuration is one frozen object that sets two paths, so the single-variable claim is true by structure. A baked image does not remove the bytes; it moves them into the image pull, which happens before any measuring code runs, so it would flatter the number for a reason the harness cannot see. Nobody warms a compile cache while re-downloading weights, so the fourth cell answers no question.
CostArm C exists only because the reconnaissance run showed this vLLM compiles at startup. A warm arm needs a primed volume, and a test has to check that the arms differ nowhere else.

Measure from outside the engine

ProblemThe interesting phases are inside vLLM's startup, and part of every cold start (queue, container start, image pull) happens before any code of ours exists.
OptionsTime startup through vLLM's Python engine APIOne clock, and give all the time to the stages you can seeRun the real vllm serve as a subprocess, bracket it with a monotonic clock, split phases from its log, and get platform time by subtraction
ChoseRun the real vllm serve as a subprocess, bracket it with a monotonic clock, split phases from its log, and get platform time by subtraction
BecauseThe Python API would measure a startup path nobody deploys. With one clock you cannot detect that it is lying. The design names three; the implemented check compares the driver and worker clocks and discards a run whose in-process time exceeds its total. The platform residual is the one named cross-clock subtraction; total time to first token is itself the job's laptop-clock span minus the worker-clock warmup tail.
CostPlatform time is one residual, and it holds teardown and polling lag as well as queueing. RunPod's queue and execution durations are recorded but not used to split it. Two engine sub-phases (S4a, S4d) are not delineated by this vLLM build, so they sit merged in an unattributed row. The log patterns are tied to vLLM 0.27.1.

Interleave the arms in random triples

ProblemA rented GPU fleet changes over hours and days. Run the arms in blocks and a busy evening gets labelled as an arm effect.
OptionsBlocks: all of A, then all of B, then all of CInterleaved triples: one run of each arm per triple, order shuffled from a seed
ChoseInterleaved triples: one run of each arm per triple, order shuffled from a seed
BecauseBlocking confounds the cache with time-of-day fleet conditions, and on a rented fleet that confound can be large enough to make or erase the whole effect. The design calls interleaving its most important validity decision. Triples also allow a paired, same-host check as supporting evidence.
CostA resumed campaign must rebuild the exact schedule, so the harness refuses a resume whose stored arms disagree with the seed. The windows ended up hours apart rather than on separate days, so drift between windows is only partly covered; the post says so.

Prove each arm's cache state

ProblemA warm cache leaking into a cold arm, or a cold compile inside arm C, would still produce plausible numbers. The configuration alone does not show what was on disk.
OptionsTrust the configurationLet arm C's first campaign runs warm the cachePrime arm C outside the campaign, isolate cold paths per run, and check the cache state on every run
ChosePrime arm C outside the campaign, isolate cold paths per run, and check the cache state on every run
BecauseWithout priming, arm C's early runs compile cold and later ones do not: a mixture whose effect grows with run index, which looks like a real trend. So two priming runs go to a separate store, and the second must show the cache present and compile under one second. Cold paths are named by run id so a reused worker cannot hand one run's files to another. The handler checks whether the compile cache exists before the engine starts, because a cold compile creates that directory as it finishes; a run whose observed state disagrees with its arm is discarded.
CostPriming runs cost GPU time and are excluded from every number. Moving the check to after the engine run would look harmless but quietly discard about two thirds of a paid campaign, so the code carries a do-not-move warning.

Rank the caches by the difference's interval

ProblemThe headline question is which cache buys more. Two effects, each with its own interval, do not answer it.
OptionsCompare the two point estimatesSubtract the weight-time contrast from the compile-time contrastBootstrap the difference of contrasts on total cold start, and pick the headline by a rule fixed in advance
ChoseBootstrap the difference of contrasts on total cold start, and pick the headline by a rule fixed in advance
Because"Compile cache mattered more" is only a finding if the gap between the two effects excludes zero. The difference needs one shared unit, so it is computed on total cold start; subtracting weight time from compile time would difference two different quantities. The headline rule, lead with what transfers furthest to other infrastructure, was committed before data.
CostTotal time is noisier than the mechanism units, so the interval is wide: −10.39 s, 95% [−20.30, −5.54]. The pre-registration forbids making the ranking claim anywhere without it.

Report the shape, and what it cannot answer

ProblemCold starts are right-skewed with a heavy tail, and about 100 runs per arm cannot support every summary.
OptionsMeans and standard deviationsPublish p99 as wellDrop the host hypothesis (H4) quietly once every run lands on one hostp50, p90, p95 and a full ECDF, no p99, and H4 reported as unanswerable
Chosep50, p90, p95 and a full ECDF, no p99, and H4 reported as unanswerable
BecauseA mean is pulled by the tail. At 100 runs a p99 is one or two observations, not an estimate. Before the published campaign began (a discarded window had already shown runs piling onto one host), the pre-registration committed to publishing the host count whatever it was. The same single host made every triple host-complete, so the paired check is fully supplied.
CostThe far tail stays unresolved: the post can say that B's largest runs were longer than A's, but not why. The question of whether host placement drives the tail is lost.

Implementation flow

Capture, then build offline
A cheap reconnaissance run saves real vLLM logs and RunPod responses as fixtures. Parser, clocks, store and analysis are built and tested against them and a free stub. A disk-fill defect still cost one paid 27-run window, which was discarded.
Pre-register
Hypotheses H1 to H5, both contrasts, exclusion rules, stopping rule and headline rule go into docs/experiment.md, committed before the first paid measurement run.
Prime arm C
Two arm C runs warm the compile cache on the volume. They go to a separate store and never count.
Run interleaved triples
100 seeded triples, 300 runs, one job in flight. Every pinned setting is fixed; any change ends the experiment instead of continuing across it.
Store, never retry
One JSON line per run, appended as it lands. A failure is its own row and counts in the failure table; nothing is retried in place.
Partition, then analyse
A gate sorts rows into publishable, discarded and failed before any statistic sees them. Then seeded bootstrap intervals (10,000 iterations) on medians and contrasts.
Publish what re-derives
Figures and the post come from the committed store. A re-run reproduces the analysis file byte for byte, with no GPU.

Interview card

30 seconds. I measured where the time goes when a vLLM server starts cold on a rented GPU, and which of two caches is worth warming: the model weights or the engine's compiled code. I ran three set-ups that differ in one thing only, interleaved, about a hundred times each, and split every start into phases. The compile cache bought more than the weight cache, and it also left more memory for serving.
The 2-minute version

Everyone talks about caching the weights. But vLLM also compiles parts of the model at startup and caches that on disk, and that second cache is almost invisible unless you have operated the engine. So I asked which one matters more. I set up three arms that differ only in cache configuration: nothing cached, weights on a network volume, and weights plus a warm compile cache. I ran them as shuffled triples so platform drift could not pose as an arm effect, and I wrote down the hypotheses, the exclusion rules and how I would pick the headline before the first paid measurement run. The measuring code ran the real vllm serve and read its log, with one clock inside the worker and one on my laptop, so everything outside the worker clock, platform start-up included, is a named residual, not hidden. The answer: warming the compile cache saved about 10 seconds more per cold start than caching the weights, and the interval on that difference never crossed zero. It also left about a fifth more KV cache, because profiling no longer ran next to the compiler's memory. What it cannot tell you is anything about other hardware, or whether host placement drives the tail: every run landed on one machine, and I reported that rather than dropping the question.

Hard follow-ups

Why three arms and not two, or four?

Two arms (hub vs volume) only test the weight cache, and that was the fallback if this vLLM had not compiled at startup; it does. A to B isolates weights, B to C isolates compile with weights held fixed. The fourth cell, weights cold but compile warm, has no operational meaning. A baked-image arm would just move the bytes into the image pull, which I cannot observe.

Why pre-register a one-person experiment?

Because the git timestamp is the only evidence that the hypotheses and the headline rule came before the data. It was committed four days before the first run. Later amendments are labelled: the first-touch separation rule, written about half an hour after window one showed a 2174 s platform time, with a note on reporting the flat warmup in the same commit; the window-spacing note; and the stopping decision. None changed a hypothesis or a contrast.

What surprised you?

Two things. C reached "model loaded" 8.85 s sooner than B, on arms that differ only in compile cache. It is not weight loading: vLLM's own loading time is the same in B and C (4.57 vs 4.54 s). The gap opens before loading begins; not host, not position in the triple, and this campaign does not explain it. And "ready is not fast" was wrong here: vLLM does its warmup before answering health, so the first request is already near steady state.

What would you do differently?

What the record flags. The host question failed: a serially-submitting driver kept landing on the one machine that had the image cached, and no endpoint setting changes that. The windows were hours apart, not separate days. And the first window was thrown out because arm A's per-run weights filled the worker disk, so A failed 40% of its runs against 0% for B, which would have biased the contrast by survivorship; the worker now empties cold directories before and after each run.

What does this not tell you?

The seconds for any other GPU, model, engine version, region or provider. Anything about many replicas starting at once and contending for the same volume; every run was one replica alone. Anything past p95. And whether host placement drives the tail.

So should everyone warm the compile cache?

It is the better buy and the more fragile one. It costs nothing to store, but any change to engine version, model, hardware or flags invalidates it, so every upgrade pays the cold compile again unless warming is built into the deploy. The weight cache is a volume you rent every month whether you scale or not.

Limits: do not claim more. One provider, one GPU model, one model, one engine version, one region, one host. The seconds do not transfer; the mechanisms do. H4 (does host placement drive the tail?) is unanswerable: all 300 runs landed on one host. Single replica, no contention. No percentile past p95; beyond it only single runs are shown. The first-touch rule that keeps the 2266.6 s run out of the ECDF (it stays in the medians) was written after seeing the data, and is disclosed as post hoc. Why C reaches "model loaded" 8.85 s sooner than B is not settled.

Recall check

Answer out loud first, then open.

Why are there three arms and not four?

The fourth cell, weights cold with compile warm, has no operational meaning, so measuring it fills a table without answering a question. A baked-image arm was also excluded: it moves the weight bytes into the image pull, which is inside the platform residual the harness cannot see.

Why are the arms interleaved instead of run in blocks?

Blocks would confound the cache with time-varying fleet conditions; a busy evening would be measured and labelled as an arm.

Why is arm C primed outside the campaign?

Otherwise its early runs compile cold and its later runs do not, making the arm a mixture whose effect grows with run index and looks like a trend.

Why does the handler check the compile cache before the engine starts, not after?

A cold compile creates the cache directory as it finishes. Checked afterwards, every healthy cold run would look warm and be discarded, and a real leak would pass unseen.

Why is the difference of contrasts computed on total cold start?

It subtracts one contrast from the other, so both must be in one unit. Weight time minus compile time would difference two different quantities.

Why can platform time only be obtained by subtraction?

Queueing, finding a machine, creating the container and pulling the image all happen before any measuring code exists. So it is total time on the laptop clock minus time on the worker clock. That residual also holds handler set-up, teardown and the driver's 5 s polling; RunPod's own queue delay was only about 0.13 s.

Why is a failed run never retried in place?

A retry quietly replaces slow or unlucky runs with faster ones and makes the distribution look better than it is. Failures are their own rows and are counted per arm.

Why does the warm compile cache leave more KV cache?

vLLM sizes the KV cache from free memory measured during a profiling pass. On a cold arm the compiler's working set is resident during that pass, so less memory looks free, and the smaller cache stays for the replica's life.
