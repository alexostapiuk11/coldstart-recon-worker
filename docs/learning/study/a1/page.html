Where a vLLM cold start goes

Read first: LLM serving on a GPU

Where does a cold vLLM start on a rented GPU spend its time, and which empty cache is worth warming more: the weights or the compiled GPU code? One also bought serving memory (KV cache).

Answer first

I measured where the time goes when a vLLM server starts cold on a rented GPU, and which of two caches is worth warming: the model weights or the engine's compiled code. I ran three set-ups differing in one thing only, interleaved, a hundred times each, and split every start into phases. The compile cache saved about 10 seconds more per cold start than the weight cache, 95% interval 5.5 to 20 seconds more, and it left about 20% more KV cache for serving.

Need to know first

C1Arms A, B and C

Three cache set-ups. A: weights from the model hub, compile cache cold. B: weights from a network volume, compile cache cold. C: weights from the volume, compile cache warm.
Used by: D1 Three arms, one variable · D4 Check each arm's cache state

C2Triples

One run of each arm, in an order shuffled from a seed. 100 triples make the 300 runs, so a busy hour on the rented GPUs falls on all three arms.
Used by: D3 Interleave the arms in random triples

C3Contrast, and difference of contrasts

A contrast is the difference of two arms' medians, with a 95% bootstrap interval (resample the runs 10,000 times, keep the middle 95%): A minus B is the weight cache's saving, B minus C the compile cache's. Their difference, (A minus B) minus (B minus C), ranks the caches only if its interval excludes zero; negative favours the compile cache.
Used by: D1 Three arms, one variable · D5 Rank the caches by the difference's interval

C4Two clocks and the platform residual

Clock A (laptop) brackets the whole job; total cold start is its span minus the worker-clock warmup after the first request. Clock B (worker) starts just before vllm serve is launched. Platform time = total minus clock B time, the one allowed cross-clock subtraction: queue, container start, handler set-up, teardown, polling lag.
Used by: D2 Measure from outside the engine

C5Percentiles and the ECDF

p90 is the time 90% of runs finish within; p50 is the median. An ECDF plots every run (seconds across, share finished up), so the tail stays visible.
Used by: D6 Report the shape, and what it cannot answer

C6The five hypotheses

H1: weight handling is over half of worker-clock time through the first request in arm A. H2: volume weights cut it materially. H3: compiling is a non-trivial part of engine start, and a warm cache cuts it. H4: host differences drive how far p95 sits above the median. H5: a warm compile cache leaves more KV cache.
Used by: D6 Report the shape, and what it cannot answer

C7Pre-registration

Hypotheses, contrasts, which runs to throw out, when to stop and how to pick the headline, committed in docs/experiment.md before any paid measurement run, four days before the published campaign's first run; later additions are dated in git.
Used by: D5 Rank the caches by the difference's interval

Requirements that drove everything

R1Name every phase, hide nothing

Split one cold start into named phases, and label time that cannot be attributed instead of hiding it.
The caches act on different phases (weights on loading, compile on engine start), so one "startup" bar would hide half the experiment.
Answered by: D2 Measure from outside the engine

R2One change per comparison

Any two set-ups compared differ only in cache configuration: same image, entrypoint and engine flags.
Otherwise a difference cannot be pinned on a cache.
Answered by: D1 Three arms, one variable · D3 Interleave the arms in random triples · D4 Check each arm's cache state

R3Spread and intervals, not means

Report each arm's spread as percentiles, and give every comparison its own interval.
Cold starts are skewed with a heavy tail, so a mean describes no real run. "Cache X matters more" needs its own interval, not two point estimates side by side.
Answered by: D5 Rank the caches by the difference's interval · D6 Report the shape, and what it cannot answer

R4Rules before data

Commit the hypotheses, which runs get thrown out, when to stop and how the headline is chosen, before the first paid measurement run.
Git timestamps then show the rules came before the data, and the headline cannot be picked by which result cost the most effort.
Answered by: D5 Rank the caches by the difference's interval · D6 Report the shape, and what it cannot answer

R5Tested code, laptop-checkable numbers

Run on paid GPUs only code already tested offline, and let anyone re-derive every number on a laptop.
The whole budget was $200, and debugging on live GPUs eats it. A number a reader cannot re-derive must be taken on trust.
Answered by: no decision. It is met by process: the flow step "Capture, then build offline" tests the code on recorded logs, API responses and a free fake engine before paid runs, and "Publish what re-derives" re-derives every figure with no GPU.

Core decisions

D1Three arms, one variable

Serves: R2 One change per comparison
Seen in: F1 Where each arm's median cold start goes · F3 The two effects, each measured on its own · F5 KV cache left for serving, by arm
Problem
Two caches start empty: the weights and the compiled code. To rank them, each comparison must change one thing only.
Options
Two arms: hub vs volume weightsAdd a baked-image arm, weights inside the container imageAdd the fourth cell: weights cold, compile cache warmOne variable, cache configuration, at three levels: A, B, C
Because
A to B isolates the weight cache, B to C the compile cache; one frozen configuration makes the single-variable claim true by structure.
Cost
Arm C needs a primed volume, and a test checks that the arms differ nowhere else.
Full reasoning and cost
Because
A to B isolates the weight cache. B to C isolates the compile cache with weight handling held constant. The configuration is one frozen object that sets two paths, so the single-variable claim is true by structure. A baked image only moves the bytes into the image pull, inside the platform residual the harness cannot split, so it would flatter the weight time unseen. Nobody warms a compile cache while re-downloading weights, so the fourth cell answers no question.
Cost
Arm C exists only because a trial run before measuring showed this vLLM compiles at startup. A warm arm needs a primed volume, and a test has to check that the arms differ nowhere else.

D2Measure from outside the engine

Serves: R1 Name every phase, hide nothing
Seen in: F1 Where each arm's median cold start goes
Problem
vLLM's interesting phases are internal, and part of every cold start (queue, container start, image pull) happens before our code exists.
Options
Time startup through vLLM's Python engine APIOne clock, and give all the time to the stages you can seeRun the real vllm serve, bracket it with a worker clock, split phases from its log, and get platform time by subtraction
Because
Timing the real vllm serve from outside measures the path people deploy, and a second clock lets a lying run be caught.
Cost
Platform time is one residual that also holds teardown and polling lag; two engine sub-phases stay merged.
Full reasoning and cost
Because
The Python API would measure a startup path nobody deploys. With one clock you cannot detect that it is lying; the implemented check compares the laptop and worker clocks and discards a run whose total leaves no room for a network round trip.
Cost
Platform time is one residual holding teardown and polling lag as well as queueing. RunPod's queue and execution durations (clock C) are recorded but not used to split it. Two engine sub-phases (device init and KV allocation) are not delineated by this vLLM build, so they sit merged in an unattributed row. The log patterns are tied to vLLM 0.27.1.

D3Interleave the arms in random triples

Serves: R2 One change per comparison
Problem
Conditions on rented GPUs change over hours and days. Run the arms in blocks and a busy evening gets labelled as an arm effect.
Options
Blocks: all of A, then all of B, then all of CInterleaved triples: one run of each arm per triple, order shuffled from a seed
Because
Running all of one arm first would mix the cache effect with time-of-day conditions on the platform.
Cost
A resume must rebuild the exact schedule; drift between windows hours apart is only partly covered.
Full reasoning and cost
Because
Blocking confounds the cache with time-of-day conditions, and on rented GPUs that confound can be large enough to make or erase the whole effect. The design calls interleaving its most important validity decision. Triples also allow a paired, same-host check as supporting evidence.
Cost
A resumed campaign must rebuild the exact schedule, so the harness refuses a resume whose stored arms disagree with the seed. The windows ended up hours apart rather than on separate days, so drift between windows is only partly covered; the post says so.

D4Check each arm's cache state

Serves: R2 One change per comparison
Problem
A warm cache leaking into a cold arm, or a cold compile inside arm C, would still produce plausible numbers. The configuration alone does not show what was on disk.
Options
Trust the configurationLet arm C's first campaign runs warm the cachePrime arm C outside the campaign, isolate cold paths per run, and check the compile-cache state on every run
Because
Unprimed, arm C's early runs compile cold and later ones do not, which looks like a real trend.
Cost
Priming runs cost GPU time and are excluded from every number.
Full reasoning and cost
Because
Without priming, arm C's early runs compile cold and later ones do not: a mixture whose effect grows with run index, which looks like a real trend. So two priming runs go to a separate store, and the second must show the cache present and compile under one second. Cold paths are named by run id so a reused worker cannot hand one run's files to another. The cache state is checked before the engine starts, since a cold compile creates the directory as it finishes; a run whose state disagrees with its arm is discarded.
Cost
Priming runs cost GPU time and are excluded from every number. Moving the check to after the engine run would look harmless but quietly discard about two thirds of a paid campaign, so the code carries a do-not-move warning.

Because

Implementation flow

Capture, then build offline
Real vLLM logs and RunPod responses from a cheap trial run are saved as test inputs; the code is tested on them and on a free fake engine. A disk-fill defect still cost one discarded 27-run window.
Pre-register
Hypotheses, contrasts and rules are committed in docs/experiment.md before the first paid measurement run.
Prime arm C
Two arm C runs go to a separate store and never count; the second must show compile under one second. Each run checks its compile cache before the engine starts, because a cold compile creates it as it finishes.
Run interleaved triples
100 seeded triples, one job in flight. Any change to a pinned setting ends the experiment.
Store, never retry
One JSON line per run, appended as it lands. A failure is its own row, never retried: a retry would swap slow or unlucky runs for faster ones.
Partition, then analyse
A gate sorts rows into publishable, discarded and failed before any statistic; then seeded bootstrap intervals (10,000 iterations).
Publish what re-derives
Figures and the post come from the committed store; a re-run reproduces the analysis byte for byte, with no GPU.

Interview card

30 seconds. I measured where the time goes when a vLLM server starts cold on a rented GPU, and which of two caches is worth warming: the model weights or the engine's compiled code. I ran three set-ups differing in one thing only, interleaved, a hundred times each, and split every start into phases. The 2-minute version

Everyone talks about caching the weights. But vLLM also compiles parts of the model at startup and caches that on disk, a cache few notice unless they have operated the engine. I set up three arms that differ only in cache configuration: nothing cached, weights on a network volume, and weights plus a warm compile cache. I ran them as shuffled triples so platform drift could not pose as an arm effect, and I committed my hypotheses and rules before the first paid measurement run. I timed the real vllm serve with one clock in the worker and one on my laptop, so platform start-up is a named residual, not hidden. The answer: warming the compile cache saved about 10 seconds more per cold start than caching the weights, and the interval on that difference never crossed zero. It also left about a fifth more KV cache, because profiling no longer ran next to the compiler's memory. What it cannot tell you is anything about other hardware, or whether host placement drives the tail: every run landed on one machine, and I reported that rather than dropping the question.

Hard follow-ups

Why three arms and not two, or four?

Two arms (hub vs volume) only test the weight cache: the fallback had this vLLM not compiled at startup; it does. A to B isolates weights, B to C compile with weights fixed. The fourth cell, weights cold but compile warm, has no operational meaning. A baked-image arm would only move the bytes into the image pull, which I cannot observe.

Why pre-register a one-person experiment?

The git timestamp is the only evidence that the hypotheses and the headline rule came before the data: they were committed four days before the published campaign's first run. Later amendments are dated, among them the rule separating a host's first image pull, written about half an hour after window one showed a 2174 s platform time. None changed a hypothesis or a contrast.

What surprised you?

Two things. C reached "model loaded" 8.85 s sooner than B, on arms that differ only in compile cache, while vLLM's own model-loading time is the same in B and C (4.57 vs 4.54 s): not host, not position in the triple, and this campaign does not explain it. And "ready is not fast" was wrong here: vLLM does its warmup before answering health, so the first request is already near steady state.

What would you do differently?

The host question failed: a serially-submitting driver kept landing on the one machine that had the image cached. The windows were hours apart, not separate days. And the first window was thrown out because arm A's per-run weights filled the worker disk (A failed 3 of its 9 runs, B none), which would have biased the contrast; the worker now empties cold directories before and after each run.

What does this not tell you?

The seconds for any other GPU, model, engine version, region or provider. Anything about many serverless replicas starting at once and contending for the same volume; every run was one replica alone. Anything past p95. And whether host placement drives the tail.

So should everyone warm the compile cache?

It is the better buy and the more fragile one. A compile cache costs nothing to store, but any change to engine version, model, hardware or flags invalidates it, so every upgrade pays the cold compile again unless warming is built into the deploy. The weight cache is a volume you rent every month whether you scale or not.

Limits: do not claim more. One provider, GPU model, model, engine version, region and host: the seconds do not transfer; the mechanisms do. H4 (does host placement drive the tail?) is unanswerable: all 300 runs landed on one host. Single replica, no contention. No percentile past p95. The first-touch rule that keeps the 2266.6 s run out of the ECDF (it stays in the medians) was written after seeing the data and is disclosed as post hoc. Why C reaches "model loaded" 8.85 s sooner than B is not settled.

Recall check

Answer out loud first, then open.

B and C differ only in the compile cache. Which chart segment should change, and which other one changed?

Only compile should move, and it does: 18.79 to 0.33 s. The launch segment also shrank, 30.35 to 21.34 s, though vLLM's own loading time is the same in B and C (4.57 vs 4.54 s). The campaign does not explain it.

On the one-run view, where does clock B start, and what lands in platform time?

Between steps 4 and 5: the probe starts clock B just before launching vllm serve. Platform time is everything the laptop clock sees outside it: queueing, finding a GPU, starting the container and handler set-up before; teardown and the driver's 5 s polling after.

Why is arm C primed outside the campaign?

Otherwise its early runs compile cold and its later runs do not, making the arm a mixture whose effect grows with run index and looks like a trend.

Why is the compile cache checked before the engine starts, not after?

A cold compile creates the cache directory as it finishes. Checked afterwards, every healthy cold run would look warm and be discarded, and a cold compile inside arm C would pass as warm.

How is a contrast obtained, and why does the ranking need a third number?

Subtract the medians of two arms that differ in one cache, with a bootstrap interval. Which cache saves more is a claim about the difference of the two contrasts, so it needs its own interval, on one shared unit: total cold start.

If the difference's interval had run from −20 to +3 s, what could you claim?

Not the ranking: no difference, or a slightly larger weight-cache saving, would still fit, and the design makes the ranking a finding only if the interval excludes zero. Each cache's own saving, with its interval, could still be reported.

Which requirement breaks if the arms run in blocks, and what protects it?

R2, one change per comparison: in blocks, time-of-day platform conditions change along with the cache. Interleaved triples protect it, with one frozen cache configuration and the per-run check of each arm's compile-cache state.

Why is a failed run never retried in place?

A retry quietly replaces slow or unlucky runs with faster ones and makes the distribution look better than it is. Failures are their own rows and are counted per arm.

Why does the warm compile cache leave more KV cache?

vLLM sizes the KV cache from free memory measured during a profiling pass. On a cold arm the compiler's working set is resident during that pass, so less memory looks free, and the smaller cache stays for the replica's life.
