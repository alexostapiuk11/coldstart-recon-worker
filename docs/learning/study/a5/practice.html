Objectives

  • Write y = Wx + (α/r)B(Ax), give A and B's shapes for one projection, and size a rank-16 adapter within 10% (about 63 MiB).
  • Draw the 24 GB card at 1, 8 and 64 slots and compute the KV tokens left at 64 slots from the budget (5.89 GiB, 42,864 tokens).
  • Explain in 60 seconds why a batch spanning 64 adapters costs more than one sharing an adapter, and say which parts are measured.
  • Quote the two costs at 64 slots (−1,290 and −450 tokens/s), say which is paired within a start, and why.
  • Apply the knee rule to the doubling table, then turn a KV ceiling into a tenant bound with Little's law (250 at 8,192 tokens).
  • State what "8 tenants per GPU" does and does not mean, and name what would have to be measured to say more.

Check yourself first

Three questions the study page prepared you for. Answer out loud, then open.

1A 24 GB GPU serves an 8B model in bf16. Roughly how much memory is left for the KV cache, and how does vLLM decide its size?

Show the answer

The weights take about 16 GB (8B numbers at 2 bytes), so at most about 8 GB is left before runtime memory. vLLM profiles a forward pass and gives what remains of its memory budget to the KV cache.

If you missed it, review KV cache.

2Why does decoding 64 requests together take only a little longer per step than decoding one (general GPU behaviour, not measured in this repo)?

Show the answer

A decode step reads every weight from GPU memory once, whatever the batch size, so, while decode is memory-bound, a bigger batch adds little time per step (general GPU behaviour, not measured in this repo). That is the batching the adapters then break up.

If you missed it, review Continuous batching.

3A 90% bootstrap interval for a median difference is [−1.87%, +0.95%] and the margin is ±5%. Is that equivalent, and what else makes "no difference found" trustworthy?

Show the answer

Yes, it lies inside the margin. You also need evidence the method can resolve ±5%: a real-versus-real check whose interval also fits inside ±5%. Without it the verdict is inconclusive, not a pass.

If you missed it, review Validation gate.

Estimation drills

Do the arithmetic on paper first, then open the worked steps.

How many adapter slots fit beside one 8,192-token request?

RTX 4090 (23.52 GiB), Qwen3-4B, memory budget 0.80. The server must hold at least one 8,192-token request in its KV cache. Use the measured 79 MiB per slot at rank 16. How many slots fit at rank 16, and what would rank 64 give if slot memory scales with rank?

Worked answer
  1. Budget = 0.80 × 23.52 = 18.81 GiB (the logged figure).
  2. Fixed memory: base weights 7.55 GiB plus runtime and activation 0.44 GiB, both derived, = 7.99 GiB. Left for slots plus KV: 18.81 − 7.99 = 10.82 GiB.
  3. One 8,192-token context at 144 KiB a token = 8,192 × 144 / 1,048,576 = 1.125 GiB. Slots may use 10.82 − 1.125 = 9.695 GiB (about 9.70).
  4. Rank 16: 9.695 / 0.0771 GiB per slot = 125.7, so 125 slots.
  5. Rank 64 (assumption: slot memory scales linearly with rank; the 1.254 overhead factor is measured at rank 16 only): 4 × 79 = 316 MiB = 0.31 GiB per slot, 9.695 / 0.31 = 31 slots. Theory alone (4 × 63 = 252 MiB) gives 39.
  6. Sanity check: 64 slots at rank 64 would need about 19.75 GiB (4 × 4.94), more than the 10.82 GiB available; the harness amendment's theory figure is 15.8 GiB. Either way they do not fit.

Answer. 125 slots at rank 16 (extrapolated beyond the 64 slots measured; memory only, not throughput). About 31 at rank 64, an assumption: rank scaling of the overhead was not measured.

The memory bound if requests are 2,048 tokens, not 8,192

At 8 slots the engine logged 74,288 KV tokens; 64 requests were in flight at 203.72 completed requests a second; a tenant peaks at 0.11416 requests a second (100,000 a month, peak three times average). Using the pre-registered formula, what is the memory bound on tenants for a 2,048-token context, and does it change which bound binds?

Worked answer
  1. Requests that fit: 74,288 / 2,048 = 36.27, so 36 (at 8,192 tokens it is 9.07, so 9).
  2. Memory bound = fitting requests × request rate / (in flight × one tenant's peak rate) = 36 × 203.72 / (64 × 0.11416).
  3. Denominator 64 × 0.11416 = 7.306; numerator 36 × 203.72 = 7,333.9; ratio 1,003.8, floored to 1,003.
  4. Compare: throughput bound 1,784, memory bound 1,003 (at 8,192 tokens: 250), slot bound 8. The slot bound still binds.
  5. Caveat: 2,048 tokens is a chosen what-if. The 0.31 s time in the system was measured on 29-token requests and a real long request would stay longer, so the bound is generous.

Answer. About 1,003 tenants by memory at a 2,048-token context, against 250 at 8,192; the 8-slot bound still binds.

Deep-dive drill

Ordered easy to hard. Answer out loud, open the model answer, then the red-flag answer: the tempting reply that sounds right and is not.

Drill 1 of 12

What does rank mean in LoRA, and how big is a rank-16 adapter on Qwen3-4B?

Model answer

W stays frozen and the output is y = Wx + (α/r)·B(Ax), with A shaped r × in and B shaped out × r. Rank r is the inner width. Parameters are r × (in + out) per projection: 917,504 a layer and 33,030,144 over seven projections and 36 layers, which is 63 MiB at 2 bytes (computed from the repo's Qwen3-4B shape constants). The measured slot took 79 MiB; the sources do not explain the 16 MiB gap.

Red-flag answer

"Rank is the number of layers adapted", "an adapter is a few KB", or quoting 63 MiB as a measurement, or inventing a cause for the 16 MiB.

Drill 2 of 12

What do max_loras, max_cpu_loras and max_lora_rank set in vLLM 0.27.1, and what were they here?

Model answer

max_loras: the number of GPU slot buffers (each sized to max_lora_rank, allocated used or not) and the cap on distinct adapters per batch. max_cpu_loras: adapters held in host memory (at least max_loras), copied into a slot on demand. max_lora_rank: the width every slot is padded to. Here max_loras = max_cpu_loras = N (1 to 64) and rank 16, so nothing swaps. This is the harness amendment's reading of 0.27.1; other versions may differ.

Red-flag answer

"max_loras is the total number of adapters the server can serve."

Drill 3 of 12

Why does KV capacity fall as slots are added, and is the fall linear?

Model answer

vLLM sizes the KV cache from what is left of its memory budget after weights, slot buffers and runtime memory, so each slot's 79 MiB buffer removes about 561 tokens. Measured: 78,208 tokens at 1 slot and 42,864 at 64, 45% fewer; (78,208 − 42,864) / 63 = 561. The fall is close to a straight line (the 32-slot point is 369 tokens, 0.6%, off the 1-to-64 chord). It only looks like a cliff on a log slot axis.

Red-flag answer

"It accelerates past 16 slots."

Drill 4 of 12

Why can KV capacity not slow this benchmark, even at 64 slots, and when would it?

Model answer

A 29-token request takes two 16-token blocks, so 64 in flight use about 2,048 tokens of 42,864 (the engine logged 4.7% KV use); the scheduler never waits for blocks. It would bind with long contexts: at 8,192 tokens the cache holds 9 requests at 8 slots and 5 at 64.

Red-flag answer

"Less KV means preemption, so it is part of the slowdown."

Drill 5 of 12

Why does a batch spanning 64 adapters cost more than one sharing an adapter, and how sure are you?

Model answer

Mechanism, consistent with the data and not measured (vLLM 0.27.1 source reading): the base weights are read once per step for all requests, while each distinct adapter needs its own small multiply over only its requests, with its own weights read (about 63 MiB each, 3.9 GiB for 64, in theory). Measured: spread costs 1,290 tokens/s more than concentrated at 64, in the same starts. How that splits between extra bytes, tiny multiplies and launches was not measured.

Red-flag answer

"Adapters are swapped in and out" (nothing swaps here), "it is memory", or stating the kernel mechanism as a measurement.

Drill 6 of 12

Why does the one-adapter regime also slow down, by 450 tokens/s at 64 slots, and why is that not memory?

Model answer

By the repo's reading of the 0.27.1 source the LoRA kernels launch max_loras + 1 slices whatever the batch holds (65 at 64 slots, 2 at 1); empty ones exit early but are still launched. KV never binds at this shape. How much of the 450 that explains is unmeasured: the --specialize-active-lora diagnostic ran out of GPU memory in graph capture (4.5 times as many graphs) and was cut, so host-side bookkeeping could also contribute.

Red-flag answer

"KV capacity fell 45%, so it is memory", or claiming the launch grid explains the 450.

Drill 7 of 12

Why run both regimes inside every server start rather than sweeping configurations?

Model answer

Slot count and in-batch cap are one knob, so configuration cannot hold registered fixed while active changes; traffic can. Pairing inside a start cancels start-to-start variation, so the heterogeneity interval is tight ([−1,309, −1,274]). The slot cost compares different starts and is wider ([−486, −425]).

Red-flag answer

"Set max_loras to 1 and register 64 adapters." With a larger max_cpu_loras that is the swapped mode, a different experiment.

Drill 8 of 12

How do you turn a KV ceiling into a tenant bound?

Model answer

Little's law: requests in the system = rate × time. At 8 slots 64 in flight at about 204 completed a second means about 0.31 s each. A tenant at peak (0.114 requests a second) keeps about 0.036 in the system. KV room for 9 requests of 8,192 tokens divided by 0.036 gives 250 tenants. It is generous: a real long request stays longer than 0.31 s.

Red-flag answer

"KV tokens divided by tokens per request is the tenant count" (forgets time in the system).

Drill 9 of 12

Is "8 tenants per GPU" the product's capacity?

Model answer

No. It is the slot bound: the largest N below the knee, with every adapter resident, 64 requests in flight and one short request shape. It is a floor on tenants. How many customers fit depends on how often they overlap and on swapping adapters from host memory; neither was measured. $101.24 a month is an upper bound on cost per tenant; if the first crossing is noise the bound is 16 and the cost halves.

Red-flag answer

"Yes, so a 4090 serves 8 customers at $101 each."

Drill 10 of 12

Why license synthetic adapters with an equivalence gate, and what does a pass not license?

Model answer

Serving cost is set by shape (rank, modules, base), and a dense multiply does the same work for any values. The one known path from values to cost, what the model generates, is closed by ignore-EOS and prefix caching off. The gate checked it at 8 slots with a 90% interval inside ±5% plus a real-versus-real resolution check. A pass licenses nothing about quality, other ranks or other bases.

Red-flag answer

"Random weights are fine because LoRA weights do not matter."

Drill 11 of 12

The 8-to-16 loss is 10.7% with interval [9.2%, 11.5%]. Defend the knee rule.

Model answer

The rule and tau were committed before the first measured run (tau was signed off after reconnaissance): the first doubling whose point estimate exceeds τ = 10%. Requiring the interval to clear τ would move the knee to 16 to 32 and double tenants on a noisy drop; the point rule errs toward fewer tenants, the cautious side for capacity. Report both: if the crossing is noise the slot bound is 16 and cost per tenant is $50.62.

Red-flag answer

"10.7 is above 10, so it is proven."

Drill 12 of 12

You must serve tenants with ranks from 8 to 64 on 4090s. What breaks first, and what do you measure?

Model answer

Slots are padded to max_lora_rank, so one rank-64 tenant makes every slot rank-64 and slot memory grows with rank; the amendment estimates 64 slots at rank 64 at about 15.8 GiB, which does not fit beside the weights. Pooling GPUs by rank is one option (my suggestion, untested here). Measure: co-active adapters per step, swap rate and latency if you use host memory, TTFT p95 per tenant, and throughput against active adapters at your real concurrency and request shape. None of this was measured here.

Red-flag answer

"Just set max_loras to the number of tenants."

Design scenario

You run a fine-tuning product: 2,000 customers, each with a rank-16 LoRA adapter on Qwen3-4B, 100,000 requests a month each, peak three times average, TTFT p95 under 1 s. Design the serving tier on RTX 4090s: how many GPUs, how adapters are placed, and what you measure before you trust the plan.

Outline of a strong answer
  1. Demand: 2,000 × 0.114 = 228 requests/s if every customer peaked together (pessimistic). Measured: 203.72 requests/s at 8 adapters in a batch, 64 in flight, 13-token prompts and 16-token outputs. That is a different shape, so re-measure; at least two GPUs on that bound.
  2. Co-active adapters in a batch, not registered adapters, drive cost. The knee (8 to 16) was measured with every adapter resident. Route a customer's traffic to a bounded set of GPUs (affinity) so a batch holds few distinct adapters. A design suggestion, not tested here.
  3. More customers than slots needs max_cpu_loras above max_loras and swapping adapters into slots on demand. Not measured: treat swap-in rate and its latency as the main risk until you measure it.
  4. Memory: at rank 16, 16 slots take 16 × 79 MiB = 1.2 GiB of KV, small. Long contexts bind earlier through Little's law. Slots are padded to max_lora_rank, so keep ranks uniform per server.
  5. Failure modes: thrash when co-active customers exceed slots (swap latency lands in TTFT), noisy neighbours (each added co-active adapter slows everyone), cold adapter fetches, a hot customer better served by a dedicated model.
  6. Measure first, pre-registered: co-active adapters per step on real traffic; swap rate and p95 swap latency; throughput against active adapters at real concurrency and request shape; TTFT p95 per customer; KV use at real contexts.
  7. Cost: GPUs × $1.1095 × 730 hours / customers. State which bound applies and that the whole-model neighbours came from a simulator that failed validation.
Pitfalls to check your answer against
  • Quoting 8 tenants per GPU as capacity.
  • Reusing 203.72 requests/s for production request lengths.
  • Assuming swapping is free: only the all-resident case was measured.
  • Mixing ranks on one server, so every slot pays the largest.
  • Treating artifact 4's neighbouring bars as findings.

Lab

Runs on your machine

Goal. Re-derive the published knee, tenants and cost from the raw data with no GPU, then change the rule (τ, context length) and watch the answer move.

No GPU or paid call. A GPU follow-up (cost not estimated here) could vary concurrency at 64 slots; it is only described here, not run, and its predicted result is untested.

Setup

  • The repo's own environment: .venv/bin/python, never uv run (it re-syncs the venv and has broken figure byte tests).
  • Inputs already committed: data/a5/campaign.jsonl, data/a5/gate.jsonl, data/a4/cost_per_tenant.json. Write outputs to a scratch folder, not over data/a5.

Steps

  1. mkdir -p scratch, then .venv/bin/python scripts/a5_analyse.py --require-a4 --out scratch/a5-analysis.json, then cmp scratch/a5-analysis.json data/a5/analysis.json.
  2. In a Python session read the campaign store as multilora/analysis.py does and call multilora.knee.knee on the spread throughput per N at tau = 0.08, 0.10 and 0.12.
  3. For each tau note the knee interval, the slots below it, and whether the crossing is resolved (the doubling's resolved flag); also apply the rule that needs the interval to clear tau.
  4. Call multilora.economics.tenants_per_gpu with max_concurrency 36 (a 2,048-token context) instead of 9, and read the three bounds.
  5. Plot the seven KV sizes against slots on a linear and a log axis, side by side.

Record

  • Knee interval and slot bound at each tau
  • Whether each crossing is resolved, and the first resolved crossing
  • Memory bound at 2,048 and at 8,192 tokens
  • Cost per tenant at each slot bound
Expected result and what it shows

Expected. cmp prints nothing. Tau 0.10: knee 8 to 16, slot bound 8, the 16 crossing unresolved; the interval rule gives 16 to 32. Tau 0.08: knee 8 to 16, and the 16 crossing is resolved. Tau 0.12: knee 16 to 32, slot bound 16, $50.62. At 2,048 tokens the memory bound is 1,003, still above the slot bound. KV is close to a straight line on linear axes.

Shows. The headline is a function of a rule fixed in advance; every published number re-derives from committed data; slot memory is linear in slots.
