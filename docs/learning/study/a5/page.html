How many LoRA adapters actually fit on one GPU

Read first: LLM serving on a GPU · How these experiments earn trust

When one GPU serves many customers' fine-tunes as LoRA adapters on one shared base model, what does each added adapter cost: holding it on the GPU, or serving it in the same batch as the others? How many tenants does that leave per GPU, at what price? Measured on Qwen3-4B, one RTX 4090, vLLM 0.27.1.

Answer first

I measured how many customers' LoRA fine-tunes one GPU can serve on a shared base model, and found the cost is mostly how many share a batch, not how many you load. I split the two by running every server start with the load on one adapter and spread over all of them; at the top of the sweep, mixing cost about three times what holding the adapters did. By a knee rule fixed in advance, past about 8 adapters active in the same batch each doubling costs over a tenth of throughput. That makes 8 a floor on tenants per GPU with every adapter resident, not a capacity claim: real counts depend on how often customers overlap, which I didn't measure. Synthetic adapters were licensed by a pre-registered gate that needed two disclosed extensions before it could pass.

Need to know first

C1LoRA adapter and its rank

A fine-tune stored as two small matrices added beside each of seven projections in every layer, instead of a whole new model: each slot's buffers took 79 MiB here (measured), against 7.63 GiB for the loaded model at 1 slot, so one base model can host many. Rank (16 here) is the matrices' width. vLLM computes every adapter at the slot's buffer rank, so the work is set by shape, not by the numbers inside.
Used by: D3 License synthetic adapters with an equivalence gate

C2Registered versus active, and the slot cap

Registered: loaded into one of max_loras GPU slots; each slot's weight buffers take GPU memory whether used or not. Active: the distinct adapters among requests batched together right now. In vLLM 0.27.1 max_loras is also the cap on distinct adapters per batch, so the two are one knob.
Used by: D1 Separate the two counts by traffic, inside one start

C3Heterogeneity cost and registered-slot cost

Concentrated regime: all load on one adapter. Spread: round-robin over all N. Heterogeneity cost at N = spread minus concentrated, in the same start. Registered-slot cost = concentrated at N minus concentrated at 1 slot, across starts: what slots cost when one adapter still carries all the load. At 64 slots: −1,290 (median of the paired gaps) and −450 (3,127 against 3,577 at 1 slot).
Used by: D1 Separate the two counts by traffic, inside one start · D2 Report memory as capacity; name the slot cost

C4The knee

Loss per doubling: m(N) = 1 − T(N) / T(N/2), with T the spread regime's throughput. The knee is the first N whose point estimate exceeds τ = 10%, fixed in advance; it lies between N/2 and N, because the sweep only doubles. Slots below it set the slot bound on tenants.
Used by: D5 A knee rule that errs toward fewer tenants · D6 Price adapters beside whole models, labelled

C5Little's law, as used here

Requests in the system = arrival rate × time each spends there. At 8 slots, 64 in flight and about 204 completed a second means about 0.31 s each. One tenant at peak, 0.114 requests a second, keeps about 0.036 requests in the system; KV room for 9 long (8,192-token) requests then fits 250 tenants. A real long request would stay longer than 0.31 s, so that bound is generous.
Used by: D2 Report memory as capacity; name the slot cost · D5 A knee rule that errs toward fewer tenants

C6Equivalence gate: pass, fail, inconclusive

Per start: (synthetic − real) / real for TTFT p50 and throughput. Pass: the median's 90% interval lies inside ±5% for both. Resolution check: the second real phase against the first must also fit ±5%; if not, the gate cannot resolve its own ±5% margin, so the verdict is inconclusive, not pass. Resolved but not inside: fail.
Used by: D3 License synthetic adapters with an equivalence gate · D4 Inconclusive twice: enlarge, then replace, both disclosed

Requirements that drove everything

R1Split loaded from active

Split what adapters cost into what registering them costs and what serving many of them in one batch costs, inside the same server start.
Most benchmarking conflates adapters loaded with adapters active together. The design's prior was that mixing adapters in a batch costs more than loading them, and only a split can test it.
Answered by: D1 Separate the two counts by traffic, inside one start · D2 Report memory as capacity; name the slot cost

R2Synthetic adapters, checked first

Sweep with synthetic adapters only after a pre-registered check shows they serve like real ones.
The sweep needs 64 adapters of one shape for one base model; of 261 public adapters for Qwen3-4B, 7 qualified. Without a check, "those aren't real adapters" stays open.
Answered by: D3 License synthetic adapters with an equivalence gate · D4 Inconclusive twice: enlarge, then replace, both disclosed

R3Capacity rules fixed in advance

Fix the knee threshold, the gate's margin and verdict rule, the SLO and the tenant assumptions before the first measured run; later changes are dated amendments.
Otherwise the knee, and the tenants per GPU it sets, could be tuned after the data.
Answered by: D3 License synthetic adapters with an equivalence gate · D4 Inconclusive twice: enlarge, then replace, both disclosed · D5 A knee rule that errs toward fewer tenants

R4Answer in tenants and dollars

Convert the knee into tenants per GPU and cost per tenant per month, beside artifact 4's cost of dedicated and swapped whole models, with every assumption published.
That three-way number is what a team building a per-customer fine-tune product needs; the design calls it the strongest business number in the portfolio.
Answered by: D5 A knee rule that errs toward fewer tenants · D6 Price adapters beside whole models, labelled

R5Only the adapter count varies

Hold image, model, GPU, rank, target modules, request shape and memory budget fixed; prime the compile cache per slot count and exclude any start that compiled cold.
In artifact 1 a cold compile cut KV cache capacity by about as much as 16 slots' buffers take here, so one cold start would fake a memory step.
Answered by: D1 Separate the two counts by traffic, inside one start

R6Medians, intervals, laptop re-run

Report medians across server starts with bootstrap intervals, never means, and re-derive every published number from committed data with no GPU.
Latency is right-skewed, so a mean describes no real start; a number a reader cannot re-derive must be taken on trust.
Answered by: no decision. Met by process: "Analyse, price, publish" re-runs the analysis byte-identically from data/a5 and artifact 4's committed cost file, with no GPU.

Core decisions

D1Separate the two counts by traffic, inside one start

Serves: R1 Split loaded from active · R5 Only the adapter count varies
Seen in: F1 Throughput as adapters are added: one active, or all · F3 At 64 adapters: mixing versus merely holding them
Problem
In vLLM 0.27.1 one setting, max_loras, is both the number of GPU slots and the cap on distinct adapters per batch, so configuration cannot hold registered fixed while active changes.
Options
Sweep registered adapters only, conflating the two counts as most benchmarking doesHold extra adapters in CPU memory and swap them into slotsAssign requests to adapters at randomRun both regimes in every start: one adapter, then all N round-robin, in a shuffled order
Because
vLLM's one knob cannot separate the two counts; traffic can, with slots, memory and the start held fixed.
Cost
The slot cost is compared across starts; the check is a once-a-second sample; the gauge's cost is bounded (about 19 tokens/s), not zero.
Full reasoning and cost
Because
Same slots, memory and start; only how many adapters the batch mixes differs, so spread minus concentrated is a difference inside one start, and start-to-start variation cancels out of it. Swapping is the resident-versus-swapped mode the design put out of scope. Random assignment of 64 requests over 64 adapters reaches about 40.6 distinct on average; round-robin keeps up to min(N, 64) in flight.
Cost
The registered-slot cost compares different starts, against 1 slot. The check that the regimes differed reads vLLM's running-adapters gauge once a second: a sample of scheduler state, not a count per batch. By vLLM 0.27.1's source the gauge may add cost to the spread regime; 24 control starts with it off put gauge-on minus gauge-off at +17 tokens/s [−19, +57]: no cost detected. A gauge cost would show as negative, so it is at most about 19 tokens/s (the post quotes the symmetric bound, 57).

D2Report memory as capacity; name the slot cost

Serves: R1 Split loaded from active
Seen in: F3 At 64 adapters: mixing versus merely holding them · F5 KV capacity falls with slots, and never binds here
Problem
The design claimed the cost was "dominated by batch heterogeneity, not by memory". Reading vLLM's source showed two flaws: at 29-token requests the KV cache can never fill, and the one-adapter regime also pays a kernel cost that grows with slots.
Options
Call the one-adapter regime's slowdown memory, as the August design didAlso split the slot cost with a --specialize-active-lora diagnostic at 1, 16 and 64 slots (planned; cut when it ran out of memory)Three parts: heterogeneity cost, registered-slot cost, and memory as a capacity ceiling
Because
KV never fills at this request shape, and the slot cost is kernel overhead, so calling either one memory would mislabel it.
Cost
The diagnostic that would split the slot cost ran out of memory and was cut; −450 tokens/s stays unsplit.
Full reasoning and cost
Because
64 requests (29 tokens each, in two 16-token blocks) need about 2,048 tokens of KV against at least 42,864, so memory never delays the scheduler. The LoRA kernels launch max_loras + 1 slices whatever the batch holds (vLLM 0.27.1 source, may differ in other versions), so the one-adapter slope is the registered-slot cost, never KV capacity. Memory becomes tenants instead, through Little's law.
Cost
The diagnostic ran out of GPU memory during CUDA-graph capture at 64 slots, at budgets 0.85 and 0.80: it asked for 4.5 times as many graphs. It was cut before the first measured run and H4 withdrawn, so −450 tokens/s stays unsplit between the launch grid, host-side bookkeeping or anything else that scales with slots.

Because (full)
Cost is set by shape: vLLM computes at the buffer rank, and a dense multiply does the same work for any values. Ignore-EOS (always 16 output tokens) and prefix caching off close the one known path from weights to cost, what the model generates. The margin is half the knee threshold, so a passing bias cannot move the knee by itself. Artifact 2's band does not fit one number, and a per-start margin would have made the gate nearly impossible to fail.
Cost (full)
The gate tested one point, 8 slots; the other sweep points rest on the shape argument. It licenses serving cost at rank 16, these seven modules and this base model, nothing about output quality or other ranks. Single-phase TTFT turned out to vary ±10–15% within a start, so the resolution check needed far more starts than planned.

D5A knee rule that errs toward fewer tenants

Serves: R3 Capacity rules fixed in advance · R4 Answer in tenants and dollars
Seen in: F2 The knee: throughput lost per doubling of active adapters · F5 KV capacity falls with slots, and never binds here
Problem
"How many adapters fit" has no answer until a rule says what counts as capacity, and the design named a threshold but neither the curve nor the rule.
Options
August's knee: a stated threshold, with the curve and rule undefinedRequire a doubling's interval to clear the thresholdFirst doubling whose point estimate loses over 10% of spread throughput; tenants = the smallest of three bounds
Because
A significance rule would push the knee, and tenants, upward on a noisy drop; the point-estimate rule errs low.
Cost
The first crossing, 10.7% [9.2%, 11.5%], is unresolved; if it is noise, tenants double.
Full reasoning and cost
Because
A loss per doubling is a ratio, so it does not depend on absolute throughput. Requiring the interval to clear 10% would miss a real but noisy drop and push the knee, and tenants, upward; the point-estimate rule errs toward fewer. Tenants = min(slots below the knee, measured throughput ÷ one tenant's peak rate, KV ceiling through Little's law), each input fixed in advance.
Cost
The 8-to-16 doubling loses 10.7% [9.2%, 11.5%]: the point crosses 10%, the interval does not clear it. If that is noise, the slot bound is 16 and cost per tenant halves. And 8 is a lower bound in any case: only the all-resident case was measured.

Interview card

30 seconds. I measured how many customers' LoRA fine-tunes one GPU can serve on a shared base model, and found the cost is mostly how many share a batch, not how many you load. I split the two by running every server start with the load on one adapter and spread over all of them; at the top of the sweep, mixing cost about three times what holding the adapters did. By a knee rule fixed in advance, past about 8 adapters active in the same batch each doubling costs over a tenth of throughput. That makes 8 a floor on tenants per GPU with every adapter resident, not a capacity claim: real counts depend on how often customers overlap, which I didn't measure. Synthetic adapters were licensed by a pre-registered gate that needed two disclosed extensions before it could pass.
The 2-minute version

Products that give each customer a fine-tune serve them as LoRA adapters on one base model, and people ask how many adapters fit. That mixes two costs: adapters held in GPU slots, and adapters active in the same batch. In vLLM one setting sets both, so I separated them by traffic: every server start ran its load on a single adapter and round-robin over all registered ones, two phases each in shuffled order, so the gap is paired inside the start. I swept 1 to 64 adapters on Qwen3-4B on one RTX 4090, 24 scheduled starts per point. The adapters were synthetic, which I only used after a pre-registered equivalence gate against 4 real ones. That gate came back inconclusive twice, once from phase-to-phase noise and once after a bad host killed 52 starts, and I extended it through two post-hoc amendments, disclosed as such, until it passed. At 64 adapters, mixing cost 1,290 tokens a second against 450 for holding the slots. KV capacity fell 45% but never bound at this request shape. By the knee rule's point estimates, each doubling past 8 adapters active in the same batch costs over a tenth of throughput, though the first crossing is unresolved. That makes 8 a floor on tenants per GPU with every adapter resident, at about $101 a month each as an upper bound; how many customers share a batch in real traffic, I didn't measure. The comparison with whole-model serving leans on artifact 4's simulator, which failed its validation, so I don't present those bars as findings.

Hard follow-ups

Why synthetic adapters, and what does that license?

There are not 64 public rank-16 adapters on the seven projections for Qwen3-4B: 7 of 261 qualified. Serving cost is set by shape: vLLM computes at the buffer rank, and a dense multiply does the same work for any values. The one known path from values to cost, what the model generates, is closed by ignore-EOS and prefix caching off. The gate then checked it at 8 slots. It licenses serving cost at this rank, these modules, this base; nothing about quality or other ranks.

Wasn't Amendment 3 a forking path?

It was data-dependent, and the post says so: I decided it after seeing the 88-start verdict. What bounds it: only the count changed, by exactly the 52 starts a host fault killed before any phase ran, back toward the size Amendment 1 had fixed; the 3 replacements that failed again were counted, not replaced; the margin and rule never moved. What it does not undo: Amendment 1 had said an inconclusive larger gate meant the August fallback, Amendment 1 was post-hoc too, and the final resolution check passes by only 0.05 points.

Why don't the cost bars count as a finding?

Dedicated and swapped come from artifact 4's simulator, which failed its pre-registered validation at exactly this operating point: 10 of 13 bins outside the band of three real repeats, 1 of 2 held-out cells passed. Its swap cost fits no single value, so the swapped bar's error direction is unknown; dedicated was never tested by the gate. The bars also cross model sizes, Qwen3-1.7B against 4B. Only the adapter bar rests on a measurement, and it is an upper bound.

Can I say one GPU serves 8 customers?

Not as a capacity claim, and the post says so next to the headline. The 8 counts adapters active in the same batch at 64 in flight, all resident, so it is a floor on tenants; real counts depend on how often customers overlap, which wasn't measured. Even as a floor it is not firm: the 8-to-16 doubling loses 10.7%, interval 9.2% to 11.5%, so the point crosses 10% and the interval does not clear it. If that is noise the bound is 16 and the cost per tenant halves; the rule was registered to err toward fewer. And only all-resident adapters were run, while vLLM can hold more in CPU memory and swap them into slots.

If memory isn't the cost, why does KV capacity fall 45%?

Each slot's weight buffers take memory the KV cache would use (78,208 tokens at 1 slot, 42,864 at 64). But 64 requests of 29 tokens use about 2,048 (two 16-token blocks each); the scheduler never waits for KV. Memory matters as capacity: at an 8,192-token context the cache holds 9 requests at 8 slots, a bound of 250 tenants, and for long contexts it would bind before throughput. That bound is generous: it uses the 29-token requests' time in system.

What would you do differently?

Build the failure-streak stop before the first paid run: without it, one bad host consumed 52 gate starts. Size the gate for its resolution check, not only its main interval: an earlier 72-start sizing left the check out, and the pilot's 24 could not resolve ±5% through phase-to-phase TTFT noise. Then the sequels the post names: rank as a variable, and resident versus swapped adapters, which turns the lower bound on tenants into a measurement.

Limits: do not claim more. Do not say "8 customers per GPU". The 8 counts adapters active in the same batch at 64 in flight with every adapter resident: a floor on tenants, not a capacity claim. One base model (Qwen3-4B), one RTX 4090, rank 16 on seven projections, one short request shape (13 prompt + 16 output tokens at 64 in flight), vLLM 0.27.1, whose source the launch-grid and gauge explanations were read from (this repo's reading, not re-checked elsewhere; other versions may differ): the numbers do not transfer, and the knee elsewhere is unmeasured. All adapters resident in GPU slots, so tenants are a lower bound and the adapter cost an upper bound. The registered-slot cost is unsplit (the diagnostic ran out of memory; H4 withdrawn). The gate tested one point (8 slots), was extended twice after its result was seen, and its TTFT resolution check passes by 0.05 points with an uninvestigated order effect. The knee's first crossing is unresolved. The regime check samples the scheduler once a second. All 191 campaign starts ran on one host, so host-to-host variation is not in the intervals. 55 gate starts and 1 campaign start failed and 4 gate starts were excluded as cold, all counted. The dedicated and swapped costs come from artifact 4's simulator, which failed validation, on a smaller model; the rate is one billing sample.

Recall check

Answer out loud first, then open.

In vLLM 0.27.1, what two things does max_loras set, and why does that force two traffic regimes?

The number of GPU slots and the cap on distinct adapters per batch. With max_cpu_loras = max_loras = N, configuration cannot change the active count while holding the registered count, so traffic does: one adapter or all N, in the same start.

Why does a batch spanning 64 adapters cost more than one sharing an adapter?

If the kernels split the batch by adapter (vLLM 0.27.1 source, not measured here), that is 64 sets of weights read per projection per step instead of one, and 64 small multiplications instead of one larger (see How it works). The campaign measured the cost's size, not its breakdown.

Why does the one-adapter regime slow down too as slots grow, and why is that not memory?

The LoRA kernels launch max_loras + 1 slices whatever the batch holds; empty slots' slices exit early but are launched (65 at 64 slots, 2 at 1; vLLM 0.27.1 source, may differ). KV never binds at 29-token requests. How much the launch grid explains is unmeasured: the diagnostic was cut.

Why is the heterogeneity cost paired within a start, and the registered-slot cost not?

Both regimes run in every start, so spread minus concentrated is a difference inside one server start and start-to-start variation cancels. The slot cost compares concentrated at N with concentrated at 1 slot, which are different starts.

The gate's real-vs-real check fits inside ±5% but synthetic vs real does not. What is the verdict, and what happens?

Fail: the gate can resolve ±5%, yet could not show synthetic within ±5% of real. The design calls that a publishable finding, and its fallback applies: public adapters only, at the count that qualifies, with a smaller sweep.

Why can random weights stand in for trained adapters, and which two settings close the remaining gap?

The work is set by shape (rank at the buffer rank, the seven projections), and a dense multiply costs the same for any values. Ignore-EOS fixes every output at 16 tokens, so weights cannot change how much is generated, and prefix caching is off, so no adapter's prompt is served from a cache another missed.

Had the knee rule required the interval to clear 10%, where would the knee be, and why was that rule rejected?

Between 16 and 32, so 16 tenants: the 32 crossing is resolved, the 16 one is not. Rejected because it misses a real but noisy drop and pushes the knee, and tenants, upward; the point-estimate rule errs toward fewer.

How does Little's law turn KV capacity into a bound on tenants?

Requests in the system = rate × time. 64 in flight at about 204 completed a second is about 0.31 s each; a tenant at peak (0.114 a second) keeps about 0.036 in the system; room for 9 long requests at 8 slots ÷ 0.036 = 250 tenants.

Which requirement does each gate amendment protect, and what do the amendments cost the claim?

R2: synthetic adapters are licensed only by a gate that can resolve ±5%. R3: each change is appended and dated, margin and rule unchanged. Cost: both were decided after a verdict, so they are data-dependent and disclosed as post-hoc.
