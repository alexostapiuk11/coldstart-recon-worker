Which duplicate-payment defense holds

Read first: How these experiments earn trust · Delivery guarantees and duplicate payments

Campaign running; results pending: this page shows requirements, design, predictions and controls only. A payment service records each payment in its own database and publishes it to Kafka; a ledger consumer applies it to balances in a second Postgres. Under real broker, process and network faults, which defense keeps every recorded payment applied exactly once: none (N), Kafka transactions (K), an idempotency key at the sink (I), or an outbox plus that key (O+I)? And at which boundary does each one stop? One laptop, public software, 760 pre-registered trials.

Answer first

I built a fault-injection harness that asks which duplicate-payment defense holds between Kafka and a Postgres ledger: none, Kafka transactions, an idempotency key at the sink, or an outbox plus that key. Each trial kills, pauses or blackholes a real broker, process or connection, and a checker that treats the source database as the authority says whether every payment was applied exactly once and at which boundary any anomaly was born. Before the campaign, a detection gate on the naive stack showed the checker catching the duplicate a commit-window kill causes and the loss a kill after the source commit causes, 10 of 10 each. The predictions were tagged before any gate or campaign trial; the campaign's results are sealed until it ends.

Need to know first

C1The four stacks and their contrasts

Same client, topic, two consumers, schema and failure policy; only the defense differs. N: dual write, at-least-once consumer. K: dual write, consumer offsets inside a Kafka transaction. I: dual write, key checked in the ledger transaction. O+I: outbox relayed by Debezium, plus the key. N→K, N→I and I→O+I each add one defense. Every producer is idempotent; O+I's needs a config override.
Used by: D1 Whole pipelines, each defense at the boundary it guards · D3 One failure policy for every mode: crash-only

C2The fault matrix: nine cells, two timings

Six faults plus a no-fault control (F0). Broker kill (F1) and pause (F2) can stress both sides; a producer blackhole (F3) and a service kill right after its source commit (F4-svc) the producer side; a random consumer kill (F4-con-r), a kill in the commit window (F4-con-t), a zombie (F5) and a lost COMMIT reply (F6) the consumer side. Random-time cells (F1–F3, F4-con-r; 30 trials per stack, as for F0) ask how often; targeted cells (a code hook; 10 trials) ask whether.
Used by: D2 Postgres commits first; the targeted kill hits every stack in one state · D4 Real faults, two timings, and a check that each one landed

C3The commit-window duty cycle

The share of a consumer's running time between its ledger COMMIT returning and its Kafka progress committing (commitSync for N and I, commitTransaction for K), measured in F0 trials over 20–50 s, the window random kills draw from (the analysis sums both consumers' windows over 60 s). A random kill duplicates only if it lands inside the window, so the duty cycle should predict the F4-con-r duplicate rate (H5).
Used by: D2 Postgres commits first; the targeted kill hits every stack in one state

C4Paired blocks, Newcombe and McNemar

A block is one cell and one seed run on all four stacks in random order: the same fault schedule and payment stream. A void trial voids its whole block, re-run with a new seed, so analysed blocks stay paired. For N vs K, the exact McNemar test uses only blocks where exactly one of the two had a duplicate (discordant); Newcombe's paired interval (method 10), over all the cell's blocks, gives a plausible range for the difference. Two contrasts are confirmatory: N vs K in F4-con-r (H5) and in F1+F2 (H4b).
Used by: D6 Pre-register, gate the detector, pair the stacks, never peek

C5The zero bound and the rule of three

The trial is the unit: payments in one trial share a fault and are never pooled. If 0 of N trials show an anomaly, the per-trial probability is below 1 − 0.05^(1/N), one-sided 95%: 0.095 at N = 30, 0.259 at N = 10. The rule of three, about 3/N, approximates it.
Used by: D6 Pre-register, gate the detector, pair the stacks, never peek

C6The detection gate, as run here

Run after the pre-registration tag, before the campaign, and not counted in it: the checker on synthetic histories with every anomaly class planted; two positive controls on N only (a commit-window kill must give a duplicate, a kill after the source commit a loss, each in at least 8 of 10 trials); a negative control of five no-fault trials per stack, all clean. All four must pass.
Used by: D5 The source is the authority; an append-only apply log shows every apply · D6 Pre-register, gate the detector, pair the stacks, never peek

Requirements that drove everything

R1Reconcile against the source

Every payment committed in the source database is applied exactly once, and every balance equals opening + credits − debits over the source's payments, computed without reading anything the consumer wrote.
The source row is the business record of the payment. Conservation alone is useless here: double-entry keeps the total constant, so a duplicate or a loss never trips it. The review upgraded the invariant to per-account reconciliation.
Answered by: D5 The source is the authority; an append-only apply log shows every apply

R2Say where each anomaly was born

Attribute every loss and every extra apply to the producer side (source ↔ Kafka), the consumer side (Kafka ↔ ledger), or unattributable.
The defenses guard different boundaries, so a count without a birthplace cannot say which one failed. Unattributable applies are reported, never split by guesswork.
Answered by: D1 Whole pipelines, each defense at the boundary it guards · D5 The source is the authority; an append-only apply log shows every apply

R3One change per contrast

Compare whole pipelines in which each contrast, N→K, N→I and I→O+I, adds exactly one defense.
The four defenses do not sit on one axis: ranked head to head, they would compare things at different layers.
Answered by: D1 Whole pipelines, each defense at the boundary it guards · D2 Postgres commits first; the targeted kill hits every stack in one state · D3 One failure policy for every mode: crash-only

R4Real faults: whether, and how often

Inject real kills, pauses and network blackholes, at code hooks in the weakest window (can it break?) and at random times (how often?), and confirm each fault took effect.
The closest prior work simulated its faults inside the application. Random faults rarely land in narrow windows, so without targeted cells a zero would mean little.
Answered by: D2 Postgres commits first; the targeted kill hits every stack in one state · D4 Real faults, two timings, and a check that each one landed

R5A zero must be able to fail

Before the campaign, show in real trials that the checker catches a duplicate and a loss when they happen, and stays silent when no fault runs.
A zero only means something if the harness can see a nonzero (controls).
Answered by: D4 Real faults, two timings, and a check that each one landed · D6 Pre-register, gate the detector, pair the stacks, never peek

R6Rules fixed before measured trials

Commit the hypotheses, fault matrix, void rules, gate and analysis before the first measured trial; no early stopping, no extension, and no anomaly output read until the campaign ends.
With 4 stacks × 9 cells, a result can be argued into shape afterwards. A pre-registration tag and dated amendments show which rules came first; reconnaissance ran before the tag and is not a result.
Answered by: D6 Pre-register, gate the detector, pair the stacks, never peek

The pipeline and the harness around it

O+I runs consumer mode I; its service writes the outbox row in the payment's own transaction and never talks to Kafka. Every Kafka client goes through its own role's proxies: one proxy at the bootstrap address would fault nothing after the first metadata response. Admin and readback traffic stays off the proxies.

Core decisions

D1Whole pipelines, each defense at the boundary it guards

Problem
The brief listed four defenses as alternatives, but the outbox guards the producer side, Kafka transactions cover only Kafka-to-Kafka work, and the key works at the sink.
Options

Because
Ranked head to head the defenses would compare different layers; whole pipelines let each contrast add exactly one.
Cost
Debezium's shipped default (a non-idempotent relay) and offsets in Postgres are explained, not measured.
Full reasoning and cost
Because
Ranked head to head the defenses would compare things at different layers. Offsets in Postgres is correct and Kafka's docs recommend it, but it guards the consumer side as I does and breaks the three-contrast structure. With Connect's default, I→O+I would change two things at once. The client assigns payment_id at the origin, and every defense depends on that.
Cost
A reader running Debezium as shipped has a non-idempotent relay (max.in.flight=1) whose retries can duplicate: stated, not measured. Offsets in Postgres and KIP-618's exactly-once source are explained or named, not measured.

D2Postgres commits first; the targeted kill hits every stack in one state

Problem
A crash between the ledger commit and Kafka's progress commit is where consumer-side duplicates are born, so the order of the two commits, and where the targeted kill lands, decide what is measured.
Options
Commit Kafka first, then PostgresKill K before any Kafka work (the first draft's hook)Postgres first in every mode; before_kafka_commit placed per mode, for K after sendOffsetsToTransaction
Because
The common order, and one state for every stack at the hook: ledger committed, Kafka progress not; for K, a real open transaction.
Cost
Kafka-first consumers are outside what is measured; K keeps Kafka's default ~100 ms commit retry.
Full reasoning and cost
Because
Postgres first is the common order; the reverse trades duplicates for losses, which the post states by reasoning and does not measure. At the first draft's hook K had no broker-side transaction, so K and N ran the same code path; the review moved it. Now every stack is hit with the ledger committed and Kafka's progress not.
Cost
Results hold for this commit order only: a reader whose Postgres commits after Kafka is outside what is measured. K's commit step also carries Kafka's default ~100 ms CONCURRENT_TRANSACTIONS retry in about two-thirds of transactions (reconnaissance); it is left as is, named, and lengthens the window H5 measures.

D3One failure policy for every mode: crash-only

Serves: R3 One change per contrast
Problem
Outcomes in F1, F2, F5 and F6 depend on what a consumer does on an error; error handling must not become a second variable between stacks.
Options
Textbook in-process recovery: abort, seek, continueCrash-only: any exception in apply or commit rolls back if it can, logs, and halts; a supervisor restarts the process after 2 s
Because
It reaches the textbook outcome, is what orchestrators do by default, and removes the skip-prone in-process path.
Cost
In-process recovery is unmeasured; the KAFKA-17582 loss hypothesis was dropped, not tested.
Full reasoning and cost
Because
For these exceptions crash-only reaches the textbook outcome, resuming from the last committed offsets, and it is what an orchestrated deployment does by default. It removes the abort, seek and continue path, where a missed seek silently skips a batch and where KAFKA-17582 would act. The exit is Runtime.halt(1) with no client closed, so every crash looks the same to the group and the coordinator.
Cost
In-process recovery is unmeasured and named out of scope. A loss hypothesis about KAFKA-17582 was dropped before pre-registration: this design gives the bug no route to the ledger, so a zero would have read as evidence it never had.

D5The source is the authority; an append-only apply log shows every apply

Serves: R1 Reconcile against the source · R2 Say where each anomaly was born
Seen in: F1 The detection gate's controls, on stack N (control, not a campaign result)
Problem
To say 'applied exactly once' and 'born here', the checker needs a truth independent of the consumer and a record of each apply's (partition, offset).
Options
A unique applied tableAn 'unknown' bucket for timed-out requestsA linearizability checkerCount each payment in the source, topic and append-only apply_log; the source resolves info; attribute by offset
Because
A unique table would hide the duplicates; the source as oracle and each apply's offset make the check complete and attributable.
Cost
No ordering check, so overdraft-style ledgers are out; info is resolvable only because this is an experiment.
Full reasoning and cost
Because
A unique applied table would hide the very duplicates N and K are expected to produce. The review dropped 'unknown' because it contradicted the source-as-authority rule. With unique IDs and commuting increments, counting each ID is a complete check, and order is not part of the invariant, so no linearizability checker is needed. The offset splits a duplicate into a redelivery or a re-send.
Cost
Order is not checked: a defense that holds here may not hold for a ledger with overdraft rules. The experiment can resolve info; a real client cannot. An apply whose offset is absent from the readback stays unattributable.

How the pieces connect

The questionCampaign running; results pending: this page shows requirements, design, predictions and controls only. A payment service records each payment in its own database and publishes it to Kafka; a ledger consumer applies it to balances in a second Postgres. Under real broker, process and network faults, which defense keeps every recorded payment applied exactly once: none (N), Kafka transactions (K), an idempotency key at the sink (I), or an outbox plus that key (O+I)? And at which boundary does each one stop? One laptop, public software, 760 pre-registered trials.

Interview card

30 seconds. I built a fault-injection harness that asks which duplicate-payment defense holds between Kafka and a Postgres ledger: none, Kafka transactions, an idempotency key at the sink, or an outbox plus that key. Each trial kills, pauses or blackholes a real broker, process or connection, and a checker that treats the source database as the authority says whether every payment was applied exactly once and at which boundary any anomaly was born. Before the campaign, a detection gate on the naive stack showed the checker catching the duplicate a commit-window kill causes and the loss a kill after the source commit causes, 10 of 10 each. The predictions were tagged before any gate or campaign trial; the campaign's results are sealed until it ends.
The 2-minute version

Teams say "exactly-once", but the usual defenses guard different boundaries: the outbox the producer side, Kafka transactions only Kafka-to-Kafka work, an idempotency key the sink. So I built four whole pipelines, each contrast adding one defense, on one laptop with public software, and a harness that injects real faults: broker kills and pauses, a producer blackhole, consumer kills at random times and at a code hook in the commit window, a zombie consumer, a lost COMMIT reply. A checker treats the source database as the authority and uses each apply's (partition, offset) to tell a redelivery from a re-send. The rules were tagged after reconnaissance and before the first gate trial, with dated amendments before the first campaign trial. H1 predicts Kafka transactions still double-post when killed after the Postgres commit. H5, the non-obvious one, predicts they make a random crash more likely to double-post, because the transaction commit widens the window between the ledger commit and Kafka's progress. A detection gate on the naive stack showed the checker sees a duplicate and a loss when they happen. The 760-trial campaign is running and I don't read its anomaly output until it ends, so today I can give you the design and the bets, not the answers.

Hard follow-ups

Do your consumers commit the database before or after Kafka, and what does that do to your duplicate rate under crashes?

Postgres first, then Kafka's progress, in every stack. A crash between the two leaves the ledger committed and the offset not, so the batch is redelivered and applied again unless the sink checks a key; the gate showed it on N, the record at (1, 646) applied again 10.1 s later. Kafka first trades duplicates for losses; that I state by reasoning, not measurement. How often a random crash lands in the window depends on the time spent there: H5 predicts K spends more, and reconnaissance saw about two-thirds of K's offset commits retried after ~100 ms. The campaign will measure the rates.

Kafka has exactly-once. Why doesn't K solve it?

A Kafka transaction commits Kafka partitions and consumer offsets atomically; Postgres is not a participant, and KIP-939, two-phase commit with external participants, had not shipped as of October 2026 (its code was reverted for Kafka 4.2). By the documented semantics, killing K after its Postgres commit and before commitTransaction makes initTransactions abort the transaction on restart and redeliver the batch; the Postgres commit stands. H1 predicts duplicates in at least 8 of 10 such trials, and in the zombie cell; the campaign will say.

Why not store offsets in Postgres in the same transaction?

It is correct, Kafka's docs recommend it, and it guards the consumer side as I does; as a fifth arm it would break the one-change contrasts. It deduplicates by (partition, offset), though, and an outbox relay's re-send lands at a new offset, so it would not catch O+I's relay duplicates. Only a key carried from the origin catches those.

How do you know a zero isn't a blind checker, or a fault that never happened?

The detection gate, run after the tag: 44 synthetic tests covering 26 class and attribution rows; on N, commit-window kills gave a consumer-side duplicate in 10 of 10 trials and kills after the source commit a producer-side loss in 10 of 10; 20 of 20 no-fault trials across the four stacks were clean. Every campaign trial also gets a per-cell manipulation check that never reads the ledger; a failed one voids the block. The gap: the positive controls ran on N only.

Your zombie consumer: which fencing stops it, and does it stop the duplicate write?

Generation fencing, at the offset commit: the group coordinator rejects a commit from an old generation. On N that is the ordinary check on commitSync in the classic group protocol; KIP-447 added the same check to K's TxnOffsetCommit. In reconnaissance on N, in all 17 F5 trials, the paused consumer's first act after unpause was a db_commit of the batch it held, then CommitFailedException about 0.1 s later. The Postgres write is another system's commit and has already happened, so fencing stops the Kafka commit, not the ledger write. Epoch fencing protects a transactional.id from its own earlier incarnation, and it is what aborts K's open transaction when K restarts. It cannot stop this zombie, because the consumer that took the partitions has its own transactional.id. For K, H1 predicts the same duplicate at TxnOffsetCommit.

What came before your pre-registration tag?

Reconnaissance A and B: the rate, the VM, Debezium's lifecycle, the F2, F5 and F6 decision rules, and the manipulation checks on real trials. Their values were frozen into the pre-registration and none is reported as a result. One recon rule (C-R: cap refusals are not rate-rule errors) was set after seeing data, and is disclosed. The tag came before any gate or campaign trial, and the analysis code and amendments A1–A4 were tagged campaign-v1 before the first campaign trial.

Limits: do not claim more. No campaign result is reported here: the campaign is running and its anomaly output is unread, so nothing here says which defense held. The gate's positive controls ran on N only; nothing yet shows K duplicating. When results exist they will hold for one laptop (combined KRaft, one Docker VM), this configuration (acks=all, Postgres before Kafka, crash-only recovery, the classic group protocol, these versions) and these faults; no overdraft rule, so ordering is untested; no database failover, disk faults or inter-broker partitions; client retries to the API are excluded; no production fault frequency is claimed. Reconnaissance numbers come from earlier environments and are not results.

Recall check

Answer out loud first, then open.

Under F4-svc, how does a dual-write stack lose a payment, and why should O+I not?

The service commits the source row, is killed before sending, and the payment never reaches the topic: a loss with a topic gap, born on the producer side. O+I writes the outbox row in the same commit, and the relay publishes it later.

Where does the commit-window hook sit for K, and why not before the Kafka work?

After the Postgres commit, the payments-applied sends and sendOffsetsToTransaction, before commitTransaction. beginTransaction() is client-local, so earlier the broker has no transaction and K would run N's code path.

In gate_cons_1, what tells the checker the duplicate was born on the consumer side?

The extra apply has the same (partition, offset), (1, 646), as the first: a redelivery. A different offset for the same payment would mean a re-send, born on the producer side.

Why pair random-time cells with targeted cells?

Random faults rarely land in narrow windows, so a random zero alone would mean little. Targeted cells ask whether a defense can break at all; random cells how often it does under realistic timing.

Suppose I shows 0 anomalies in 30 trials of a cell. What could you claim?

That its per-trial probability for that fault is below about 9.5% (one-sided 95%), on this setup. Not that the defense is safe in general.

Why does one void trial void its whole block?

So every analysed block keeps all four stacks with the same fault schedule and payment stream: the pairing the N vs K contrasts rely on. The block is re-run with a new seed.

What is the commit-window duty cycle, and why should it predict F4-con-r duplicates?

The share of running time between a ledger COMMIT returning and Kafka progress committing. A random kill duplicates only if it lands in that window, so a wider window should mean more duplicates (H5).

Why is a trial voided by a failed manipulation check but never by the checker's output?

The check asks whether the fault happened, from orchestrator, broker and process state. Voiding on the checker's output would let results decide which trials count.

Why crash-only rather than in-process recovery?

It reaches the same outcome (resume from the last committed offsets), is what orchestrators do by default, keeps error handling out of the contrasts, and removes the abort-seek-continue path where skip bugs live.

What does the passed detection gate not tell you?

Anything about K, I or O+I under faults: both positive controls ran on N. Nor any campaign rate: the gate's trials are not counted in the campaign.
