The ideas

GPU memory (HBM)

The GPU's own fast memory, fixed in size. Weights, scratch space and the KV cache share it.
Like
A kitchen counter of fixed size: the recipe book takes most of it, a prep area stays clear, order notes fill the rest.
Matters
The KV cache gets whatever weights and scratch leave, so free memory decides how many users you can serve.

Weights

The model's learned numbers, on the GPU before it can answer: about 16 GB for an 8B model at 2 bytes per parameter.
Like
The recipe book: big, never edited, on the counter before cooking starts.
Matters
Loading them sits inside the longest phase of artifact 1's cold start; a weight cache cut that phase by about 15 s.

KV cache

While generating, the model keeps the keys (K) and values (V) of every token so far instead of recomputing them. Q is not cached.
Like
Each open order's notes, one line per token: long orders take more counter, so fewer fit.
Matters
Each request holds cache in proportion to its length, so the cache divides into a number of concurrent requests; past that, new ones wait.

vLLM

The serving engine here. At startup it loads the weights, runs the model once to see what memory is left, and gives that to the KV cache.
Like
Before opening, cook the biggest order once to see how much counter cooking needs; order notes get the rest.
Matters
That memory-profiling run is in every cold start, and it sets the cache size.

Continuous batching

One copy of the model serving many users' requests at once. A fresh replica takes work as soon as it is ready.
Like
One kitchen cooking many orders at once: more dishes per hour, each a little slower.
Matters
In artifact 2, as requests in flight rose to 128, one replica's throughput rose and bent while latency rose gently.

Cold start

The wait from a request being queued to a brand-new replica's first token.
Like
Opening a kitchen from empty when a crowd arrives: get a building, bring in the recipe book, prep, then cook.
Matters
It is artifact 1's subject: a median 81.12 s with nothing cached, mostly launching and loading the model, then compiling.

Serverless GPUs

GPU replicas added when traffic needs them and removed after. Before your code runs, the platform queues the request, finds a machine and starts a container.
Like
Renting kitchens as crowds come and go, paying even while one is still opening (artifact 2 counts every replica-second).
Matters
Nothing of yours runs during the platform's part, so it is found by subtraction: total time minus the replica's own time.

torch.compile and CUDA graphs

Startup steps that pay now to be faster later. torch.compile makes faster GPU code and caches it on disk; CUDA graph capture records GPU launches for every token to replay.
Matters
A warm compile cache cut compiling to 0.33 s; graph capture took the same time in every arm, cached or not.

System views

What a replica does before it answers

One replica's cold start, in order (two short engine steps not drawn). Each cache shortens one step, as marked. Nothing before 'ready' serves a user.

  • Platform (external) — queue, machine, container; found by subtraction
  • Launch, load weights key step — weight cache shortens this
  • Compile key step — compile cache shortens this
  • Memory profiling — one forward pass; sets KV cache size
  • CUDA graph capture — flat 4 s, cached or not
  • Health check: ready — now accepts work
  • First request — first token to a user
  1. Platform → Launch, load weights
  2. Launch, load weights → Compile
  3. Compile → Memory profiling
  4. Memory profiling → CUDA graph capture
  5. CUDA graph capture → Health check: ready
  6. Health check: ready → First request

Recall check

Answer out loud first, then open.

Why does KV cache size limit concurrency, and what changes if requests get shorter?

Each request keeps K and V for every token so far, so its cache grows with its length. The cache is a token budget: shorter requests fit more of them.

Why must the engine run the model once before serving anyone?

Free memory depends on what a forward pass needs, and the only way to know is to run one at the largest batch, record the peak, and give the rest to the KV cache.

Why can a cold compile cost KV cache capacity, not only seconds?

The compiler's working memory is still on the GPU during profiling, so the profiler sees less free memory and sizes a smaller cache for the replica's whole life.

What do you trade by skipping CUDA graph capture?

Capture removes per-step launch overhead from every later token. Skipping it saves startup once and pays on every token: arguably fine for a short-lived replica only.

Why is a compile cache more fragile than a weight cache?

Its key includes engine version, model, GPU and flags, which change routinely, so an upgrade silently makes it cold. Weights never change.

What changes if a new replica lands on a host that never pulled the image?

The image pull happens before your code runs, and neither cache touches it: artifact 1's one such run took 2266.6 s.
