The ideas

GPU memory (HBM)

The GPU's own fast memory, separate from the computer's RAM, and fixed in size. Three things share it: the model weights, scratch space for one forward pass, and the KV cache.
LikeA fixed-size desk: the reference book takes most of it, a work area stays clear, and the rest holds open notebooks, one per conversation.
MattersWhat is left after weights and scratch is the cache, so "how much memory is left" and "how many users can I serve" are the same question. Artifact 1 used a 24 GB RTX 4090.

Weights

The model's learned numbers. They must be on the GPU before it can answer anything. An 8B model at 2 bytes per parameter is about 16 GB.
LikeThe reference book: big, never edited, and it has to be on the desk before work starts.
MattersMoving those 16 GB is the biggest piece of a cold start: with weights downloaded from the hub, loading took a median 45.83 s in artifact 1. Weights never change, so a weight cache stays valid until you switch models.

KV cache

When generating, the model re-reads everything written so far. To avoid recomputing it, it stores the keys (K) and values (V) for every token. Only K and V are cached; Q is not.
LikeA notebook per conversation that gains a line with every token. The desk only has room for so many open notebooks.
MattersEach active request holds cache in proportion to its length, so the cache size divides into a number of concurrent requests. Run out and new requests queue. In artifact 1, 35,792 tokens of cache at 8192 context meant 4 requests at once.

vLLM

The serving engine in these artifacts. At startup it loads the weights, runs the model once to see what memory is left, gives that to the KV cache, and reports ready. Then it serves many requests at once.
LikeA restaurant's dress rehearsal: cook the biggest order once, see how much counter space is left, then set out that many tables.
MattersThere is no way to ask a GPU how much memory will be free except to run the model once. That memory-profiling run is in every cold start, and it is where artifact 1's KV capacity number comes from.

Continuous batching

Serving many users' requests through one copy of the model at once. A fresh replica takes work the instant it reports ready.
LikeOne bus instead of a taxi each: far more riders per hour, each trip a bit slower, and a fixed number of seats (the KV cache).
MattersIt shapes artifact 2's service curve: from 1 to 128 requests in flight per replica, throughput rises and bends while latency rises gently; at 256 the engine ran out of GPU memory. It also means a just-ready replica serves real users at once.

Cold start

The wait while a machine boots and loads a model, before anyone gets an answer: from the request being queued to the first token.
LikeOpening a restaurant from an empty building each time a crowd shows up: get the keys, deliver the stock, set up the kitchen, then serve the first dish.
MattersIt is artifact 1's subject: with nothing cached the median was 81.12 s, mostly loading weights and compiling. Artifact 2 asks whether this delay changes which autoscaling signal works best.

Serverless GPUs

You rent GPU replicas that are added when traffic needs them and removed afterwards, and you pay per replica-second. Before your code runs, the platform queues the request, finds a machine, creates a container and pulls the image.
LikeCalling a taxi instead of owning a car: you pay per ride, including the meter running while it drives to you.
MattersEvery new replica starts cold. The platform part, T_platform, cannot be instrumented because nothing of yours is running yet; it is found by subtraction. A host that has never pulled the image is far worse: artifact 1's one such run took 2266.6 s.

torch.compile and CUDA graphs

Two startup steps that pay now to be faster later. torch.compile turns the model into faster GPU code and caches it on disk. CUDA graph capture records a fixed sequence of GPU operations so every token replays it without per-step launch overhead.
LikeMeal prep: chopping everything on Sunday costs an hour, but every weeknight dinner is quicker. Change the recipe and the prep is wasted.
MattersBoth sit inside every cold start: compiling took 19.01 s with an empty cache and 0.33 s with a warm one; graph capture a flat 4.00 s. A compile cache goes cold on any change of engine version, model, GPU or flags.

System views

Where GPU memory goes

One fixed pool. Weights and scratch are taken first; the KV cache gets the rest, and that sets how many requests run at once.

  • GPU memory (HBM) — fixed size, e.g. 24 GB
  • Weights — about 16 GB for an 8B model
  • Scratch space — for one forward pass
  • KV cache — K and V per token; the rest
  • Concurrent requests — how many fit at once
  1. GPU memory (HBM) → Weights: holds
  2. GPU memory (HBM) → Scratch space: holds
  3. GPU memory (HBM) → KV cache: holds the rest
  4. KV cache → Concurrent requests: divides into

What a replica does before it answers

A vLLM replica's cold start, in order. Everything up to the health check happens before any user is served.

  • Platform queue — find a machine, start a container
  • Load weights — into HBM
  • Compile — torch.compile, or its cache
  • Memory profiling — one forward pass; sizes KV cache
  • CUDA graph capture — record kernel launches
  • Health check: ready — now accepts work
  • First request — first token to a user
  1. Platform queue → Load weights
  2. Load weights → Compile
  3. Compile → Memory profiling
  4. Memory profiling → CUDA graph capture
  5. CUDA graph capture → Health check: ready
  6. Health check: ready → First request

Recall check

Answer out loud first, then open.

Why does the KV cache size decide how many requests run at once?

Each active request keeps K and V for every token so far, in proportion to its length. So the cache divides into a number of concurrent requests (35,792 tokens at 8192 context gave 4). Past that, new requests queue.

Why must the engine run the model once before serving anyone?

It cannot know how much scratch memory a forward pass needs until it tries one. It runs a profiling pass at the largest batch it must support, records peak memory, and gives the remainder to the KV cache.

Why is a serverless GPU's first request slow?

No replica is running yet. The platform queues the request, finds a machine and starts a container; then the engine loads the weights, compiles, profiles memory, captures CUDA graphs and passes its health check, all before the first token.

Why can a cold compile cost KV cache capacity, not only seconds?

The compiler's working memory is still on the GPU during the profiling pass, so the profiler sees less free memory and sizes the cache smaller, for the life of the replica.

Why not skip CUDA graph capture to start faster?

Capture removes per-step launch overhead from every later token. Skipping it (--enforce-eager) saves its startup seconds once and pays on every token after. That is arguably worth it for a replica that answers briefly and dies, not for one serving millions of tokens.

Why is a compile cache more fragile than a weight cache?

Its key includes the engine version, model, GPU and flags, all of which change routinely, so an upgrade silently makes it cold. Weights never change, so their cache stays valid until you switch models.
